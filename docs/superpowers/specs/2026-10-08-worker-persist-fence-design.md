## 1. 意图、范围与成功标准

修复审查 R1：旧 worker 在 Neo4j 排队或托管事务重试期间丢失任务租约/课程锁后，仍能提交图事务，随后 T6 才发现令牌失效。已有复现为：接管者先完成 T6，旧图回调提交一次，旧 worker 返回 `lost`。该复现使用真实 SQLite 和图调度替身，尚无真实 Neo4j 故障证据。

本任务仅调整 `persisting` 的提交协议及其所需心跳/仓储能力。成功标准是：

1. 接管已发生时，旧 worker 的未提交图事务回滚；不撤销接管者已生效贡献。
2. 提交授权检查之后到 T6 提交之前，接管更新与该提交互斥。
3. 正常路径保持图提交在先、T6 在后，且水位/草稿修订号只增加一次。
4. 故障路径明确区分提交前失败、提交结果不确定、图已提交但 T6 失败。
5. 测试证明锁和连接的退出/恢复行为；无证据的时间上限不写成保证。

不修复其他四项中严重程度发现，不改教师编辑/审核/发布协议，不新增 wire 字段、数据库迁移、环境变量或依赖，不操作现有课程资料与业务库。只复用当前受管 worktree；无并行 Agent 工作。

## 2. 根因与方案选择

当前 `workers/persist_graph.py` 在调用 `repo.write_transaction` 之前检查一次租约；回调 `_write_draft` 不携带租约有效性检查，驱动可重跑回调并在返回后自动提交。`_t6` 在图提交之后才进行 SQLite 令牌校验。

`DraftWriteGuard` 只串行化图事务，不校验 SQLite 所有者。`LeaseHeartbeat.lost` 和课程锁续约失败未传递到该提交边界；最近成功续约的单调截止规则也未落实。

已选择：**双租约守卫＋显式图事务＋SQLite 提交围栏**。

- 仅追加提交前检查或延长租约，仍留有“检查后暂停、接管、旧提交”的窗口。
- 在 Neo4j 引入 fencing epoch 需要持久化世代号并接入所有图写路径，本任务不引入该模型变更。
- 围栏复用 SQLite 的单写者串行化语义，关闭提交授权与接管之间的窗口，代价是最终提交窗口内其他 SQLite 写者等待。

## 3. 双租约守卫

任务租约和课程锁各有一个线程安全的进程内守卫。每个守卫绑定一个令牌，记录最后成功续约对应的单调时钟及永久失效标志。

- 时限沿用规格：`截止 = 最近成功续约时刻 + L - L/3`；到达或超过截止按失效处理。
- 初始有效性来自条件成立的领取/续约或剩余有效期的保守换算，不以“守卫对象刚创建”为一份新租约。
- 为避免 SQLite 等待时间被误计为新增有效期，续约计时使用调用前的单调时刻；只有成功的条件更新才更新守卫。
- 续约影响零行立即标记失效；SQLite 暂时异常保留原截止，不延长。
- 已触发本地截止的守卫不因迟到续约恢复；新领取令牌才建立新守卫。初始检查和持久化所用续约均拒绝已到期的租约复活。
- 心跳线程只更新守卫/续约数据库，不跨线程操作 Neo4j Session 或 Transaction。
- 图事务开始前、获得图守卫锁后、每条图语句发送前、每次允许的重试前、申请提交围栏后均检查两个守卫。
- 阻塞中的图语句返回后先检查有效性；失效即回滚未提交事务，不继续发写语句。服务端事务 timeout 使用两个守卫剩余预算的较小值；它不是客户端端到端截止的证明。

默认其他调用者行为保持兼容；worker 明确传入课程锁守卫并消费失败信号，正常 T6 清空任务令牌后的心跳退出不追溯撤销已经完成的结果。

## 4. 显式图事务与重试边界

为仓储新增显式事务入口，原 `Neo4jRepository.write_transaction` 保留给现有调用者。新入口提供作用域受限的语句执行和明确的 commit/rollback 生命周期，不自动在退出时提交。

worker 单次尝试的顺序：

1. 校验任务阶段、令牌、两个守卫和课程锁；按当前有效任务集合构造 `GraphScope`。
2. 开启显式 Neo4j 事务，获得现有 `DraftWriteGuard`。
3. 执行撤销本任务前次贡献、写节点、DAG 处理和写关系；所有结果在提交前消费完毕。
4. 执行 §5 的最终提交围栏。
5. 退出事务与课程锁上下文，停止所属心跳并释放资源。

本次实现不在事务内部透明重试：确认回滚的瞬时故障按现有阶段释放/退避，由下一次条件领取发起新尝试，重新获取锁、有效任务集合和完整计划。这样不复用过期作用域、已执行回调或部分结果。提交已经开始或应答不确定时不直接重放写事务。

未提交事务在异常或失效时回滚；仓储错误继续脱敏。失效结果沿用 `PersistStatus.LOST`，不新增公共状态。

## 5. 最终提交围栏与锁顺序

图构建完成后，worker 才进入 SQLite `BEGIN IMMEDIATE`。此事务内重新读取并验证：

- 任务属于本课程、阶段仍为 `persisting`、令牌相同，`lease_expires_at > unixepoch()`。
- 课程锁属于本课程、令牌相同，`expires_at > unixepoch()`。
- 两个进程内守卫仍有效。

有效期检查保守拒绝等于当前整数秒的到期边界，不延长租约。

数据库校验后、发出图 COMMIT 前再次检查两个本地守卫；若已失效，回滚两边尚未提交的事务。图 COMMIT 已发出之后按提交结果分类，不再把本地截止当作图回滚的证明。随后执行：

```text
持有尚未提交的 Neo4j 草稿事务
  → SQLite BEGIN IMMEDIATE
  → 校验任务/课程锁令牌、阶段、有效期和本地截止
  → Neo4j COMMIT
  → 同一 SQLite 连接执行 T6、水位分配、草稿修订号递增
  → SQLite COMMIT
```

如果接管更新先取得 SQLite 写锁，旧 worker 校验失败并回滚图事务。如果旧 worker 先通过围栏校验，SQLite 写锁保持至图提交和 T6 结束，接管与课程锁替换更新等待；它们随后只能看到完成后的状态，或异常退出后可恢复的旧状态。

锁顺序固定为 **Neo4j 草稿守卫 → SQLite 提交围栏**。取得 SQLite 围栏后不再发送图构建查询或等待新的草稿守卫。围栏不覆盖模型调用、候选加载、课程锁轮询、图构建或休眠退避。

将 `_t6` 的业务内容拆为 `_t6_in(database, lease)`，只使用调用者已持有的连接；原包装函数保留现有内部调用兼容性。围栏内不再次调用会打开新连接的 `leased_transaction`、`_t6` 或草稿修订号仓储，避免与自身 SQLite 写锁冲突。

在 SQLite 数据库级令牌互斥已建立后，进程内心跳失效信号不得跳过图提交结果识别：若 COMMIT 已成功，后续走 §6 的恢复分类，不将结果报告成“图已回滚”。

## 6. 故障与恢复

| 故障位置 | 图状态 | SQLite/T6 与处理 |
| --- | --- | --- |
| 开图事务前失效 | 未写 | `LOST`；不发布旧结果 |
| 图构建或围栏校验失效 | 未提交；执行回滚 | 不执行 T6，释放资源；不清理接管者成果 |
| 已确认回滚的图临时故障 | 未提交 | 退出所有上下文后按原阶段规则释放/退避；新尝试重新读取输入 |
| COMMIT 发出后应答不确定 | 可能已提交 | 回滚未完成的 SQLite 事务；不以内联重试或盲目撤销断言图未提交，按现有条件释放/接管恢复 |
| 图已提交，T6 或 SQLite COMMIT 失败 | 图已提交 | 若 T6 未生效，任务不进入 V，后续接管按任务贡献撤销/重建；结果不伪装成成功 |
| 两库提交成功 | 图与 T6 生效 | 只增加一次水位/修订号，返回正常结果；正常结束的心跳不触发补偿 |

SQLite COMMIT 应答故障时需要重新读取任务判断 T6 是否实际落地；已到 `awaiting_review`/`completed` 的任务不再次主动释放或撤销。读取也失败时记录不确定结果，保持现有状态由恢复路径判断，不猜测事务结局。

本协议不提供跨库原子提交。它阻止旧所有者越过接管进行提交，沿用 §8.4 的“图先提交、T6 后可见”和幂等接管语义。

## 7. 可用性边界与实现准入

SQLite WAL 允许既有读者读取快照，但最终围栏期间全库其他写者等待，并可能触发已有 busy timeout。不要把课程级逻辑锁描述为数据库级并行写能力。

当前 Neo4j 5.28.2 同步驱动的服务器事务 timeout 不覆盖全部提交应答等待；公开同步 Session 也无 `cancel()` 方法。因此本规格不承诺固定秒数的客户端硬取消，不采用跨线程 commit/rollback/close，也不以后台线程继续执行、外层先返回冒充取消。

实现准入要求：在独立环境注入提交阻塞、断连和应答丢失，记录 SQLite 写者等待及资源释放/恢复的实际行为。若存在持续无界提交等待导致长期全库写阻塞，保持任务未完成、停止发布；将必要的传输截止/隔离补充方案作为本任务的阻塞条件提请评审，而不是扩展到其余问答读超时修复。该可用性风险不因令牌互斥的一致性证明而自动消失。

## 9. 验收矩阵

使用可控时钟与线程屏障，不靠长时间 `sleep` 猜测竞态：

1. 新 worker 已完成 T6，旧 worker 才申请围栏：旧 worker 图 COMMIT 次数为 0，已生效图贡献不变。
2. 图语句等待期间，任务租约或课程锁分别被接管：旧未提交事务回滚，T6 次数为 0。
3. 连续续约异常超过 `2L/3`：守卫失效；迟到续约不复活；失效后没有新图语句或提交请求。
4. 最终校验后暂停旧 worker、推进过期时钟、另一个连接尝试接管：接管不穿过 SQLite 围栏。COMMIT 尚未发出且本地守卫已失效时回滚；COMMIT 已发出时识别实际提交结果。恢复后要么旧提交/T6 成功且无新领取，要么退出后由新领取恢复。
5. 两库正常提交：T6、水位和 `draft_revision` 各增一次，租约清空，心跳和锁退出正常。
6. 图事务故障、围栏校验故障、T6 故障、SQLite 提交故障：分别验证图状态、任务状态及连接/锁释放，不使用一个通用失败断言替代。
7. COMMIT 实际生效但应答丢失：不盲目回调重跑；恢复不会重复 T6，也不撤销已经确认落地的任务。
8. 原 `write_transaction` 的其他调用者与直接运行 `run_persist_stage` 的内部测试保持兼容；续约初始时刻、到期等号和进程暂停均有边界测试。
9. 真实 Neo4j 故障验证给出实际等待和退出证据；未运行时明确标记未验证，不用替身结果替代。

验证入口：`./scripts/verify.sh`（basic）、新增定向测试和既有 C09/课程锁/持久化/清理回归；实现计划给出准确测试选择与解释器。真实集成只使用独立临时库，不调用模型、不迁移用户库。完整实现验收还需按仓库门禁规则记录 full/integration 的运行或环境限制。

# ADR-006：MVP 实现任务取消，修订 ADR-005 第 2 条

- **日期**：2026-09-22
- **背景**：[ADR-005](ADR-005-task-state-machine.md) 决定保留 `cancelled` 枚举值但**不在 MVP 实现取消**，理由是取消需要 worker 协作式中断与跨存储补偿，超出 AGENTS.md §1 的 MVP 目标。随后核对参考方案原文，确认取消在方案里是**完整规格的功能**而非边角料：§6.5 接口表列有 `POST /api/tasks/{tid}/cancel`，§7.1.2 教师端界面明确写「进度条按阶段展示……可取消」。若 MVP 不实现，演示界面与方案文档对不上——这是参赛提交材料的一致性问题，不只是功能取舍。产品负责人已决定实现。
- **决定**：
  1. MVP 实现 `POST /api/v1/tasks/{tid}/cancel`，请求与响应契约在 **M0-04a** 与其余 REST DTO 一并定稿（已完成，见 `src/contracts/api.v1.yaml`）。
  2. `cancelled` 从「v1 预留、MVP 不产生」改为**正常可达终态**。ADR-005 的状态机本身不变，只是这个终态变成真实可达。
  3. **取消是协作式的**：端点只置「已请求取消」标记并立即返回，worker 在阶段边界检查该标记后进入 `cancelled`。不强杀进程，不中断正在进行的单次模型调用。
  4. 只有非终态任务可取消。对已处于 `completed` / `failed` / `cancelled` 的任务返回明确错误码，不得静默成功。取消与完成竞争时**以先到达终态者为准**，端点返回任务的当前实际状态。
  5. 已写入的部分数据必须清理或标记为废弃草稿，**不得留下半截图谱被教师看到**。跨 Neo4j 与 SQLite 的补偿失败要留下可重试状态（ADR-002）。具体清理策略在 M1-06 定稿。
  6. ADR-005 的其余内容——状态机序列、`persisting` 阶段、枚举一次定稿原则——**全部不变**，仅其第 2 条被本 ADR 取代。
- **后果**：
  - ADR-005 第 2 条作废，该文件已加修订标记。
  - ~~`src/contracts/README.md` §4.2 仍写着「预留，MVP 不产生」且「没有取消端点」~~ — 已于 2026-09-22 随 M0-07 改正，现为 §5.2「`cancelled` 是正常可达终态」。
  - `tests/README.md` 覆盖清单第 5 项的断言由「`cancelled` 在 MVP 不被产生」改为「取消请求后任务进入 `cancelled` 且不再发送事件」。
  - 新增 **M1-06**。SSE 事件需要能表达「已请求取消但尚未生效」这一中间情形，否则前端按钮无法给出反馈；该中间态在 `events.v1.md` 用 `cancel_requested` 标志表达，不占用状态枚举。
  - ADR-005 当初「枚举一次定稿、先占位」的判断被证明是对的：契约尚未开写，本次改动的迁移成本为零；若当时省掉该枚举值，现在就要把 v1 升到 v2。

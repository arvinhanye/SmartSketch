## 2. C03-1：推理是抽取耗时与 repair 的主因

逐调用数据（33 次，全部 `ok`；抽取走非流式，所以首次推理 / 可见内容时刻为空，属预期）：

- **两次关系抽取输出恰为 4096 token，其中推理也是 4096**：模型在写出任何 JSON 之前就把输出上限用完，于是触发 2 次 repair（15.7 秒、15.4 秒，推理同样占约 95%）。repair 不是 PDF 文本破碎导致的（PDF 已修复），而是推理耗尽输出预算。
- **关键路径**：
  - 实体阶段：02:57:42.000 → 02:58:06.909，24.9 秒，16 次调用，并发 4；
  - 关系与 repair 阶段：02:58:07.093 → 02:58:54.598，47.5 秒，其中最后约 13 秒只剩 repair 在跑。
- **非模型时间 18.74 秒的拆分**（L11-6 只有 3.51 秒）：
  - 解析 + 分块：任务创建 02:57:39.012 → 块写入 02:57:41.904，2.9 秒；
  - **末次模型调用完成 02:58:54.598 → `awaiting_review` 02:59:10.241：15.6 秒**，未归因。这段时间没有模型调用。worker 日志除 pdfminer 字体告警外只有一行「scrubbed 1 finished task key snapshots」（02:59:10.270），没有阶段耗时记录，本轮数据无法定位。

## 3. C02-4：一题、冷启动，不足以下链路结论

只读查询该请求的调用时间线（UTC）：

| 时刻 | 事件 |
| --- | --- |
| 02:54:51.661（推算：日志时刻 − 15015 ms） | 请求开始 |
| 02:54:51.739 → 02:54:56.673 | 查询向量，4925 ms |
| **02:54:56.673 → 02:55:04.824** | **8.15 秒没有任何调用记录**：检索、上下文组装、个人模型客户端构建等 |
| 02:55:04.824 → 02:55:06.670 | 生成；757 ms 出现推理，到 15 秒截止被切断（`timeout`），无可见内容 |

- 这是服务启动后的**第一次提问**。L15 的热请求「其余」段只有 0.1～0.9 秒，L15 启动后首个请求是 1.6 秒。这次 8.15 秒更像冷启动（Neo4j 连接与向量索引首查、个人模型客户端首次构建等），只有一个样本，不能断言「15 秒内答不完首先是链路预算分配问题」。
- 但它确实说明两点：冷启动的首问可能超时；查询向量本轮 4.9 秒，也明显高于 L15 常见的 0.4～0.6 秒。
- 推理在 757 ms 就开始、346 字推理后仍无可见内容，与「先推理后作答」的推断一致。但样本是失败调用，不能据此确认问答侧的推理 token 占比。

## 4. 工具设计问题：遇到 usage 未知就停止，对超时过严（Claude 负责）

截止切断的流天然没有 usage，按 C01 的规则整轮立即停止，13 题只测了 1 题。系统自己的计费规则（`docs/integrations.md`「调用记录」）对这类调用按「输入估算 + 输出上限」计，只允许高估。止损改为按同一规则把未知调用计为估算值即可，既不当 0，也不必整轮停：本次为 10068 + 2048 = 12116。待修（下一步 C01 补丁）。

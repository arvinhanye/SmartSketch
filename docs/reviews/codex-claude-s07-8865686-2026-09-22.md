## 新发现

### S07-R06 P1：生成物缺失时 `--check` 报错却成功退出，完整门禁假绿

- 位置：目标提交 `8865686` 的 `scripts/gen-contracts.sh:83-101`，直接触发行是 `:93`；调用方在 `scripts/verify/contracts.sh:19-22`。
- 触发：生成器已安装，而仓库尚未入库 `src/contracts/v1/generated/python/` 或 `typescript/`。循环进入“产物缺失”分支时，`"$OUT/$name（..."` 未给变量名加花括号；当前 locale 下 Bash 把相邻全角字符并入变量名，`set -u` 报 `name�: unbound variable`。随后 `EXIT` trap 的成功清理状态覆盖失败状态，脚本最终返回 0。
- 实测：`./scripts/gen-contracts.sh --check --allow-scaffold` 输出 `line 93: name�: unbound variable`，但 `GENCHECK_RC=0`；`./scripts/verify.sh` 同样打印该错误后仍输出 `All verification checks passed.`。仓库此时确实缺 `python/` 与 `typescript/`。
- 影响：R02 的核心风险重新出现：生成类型缺失或漂移时 CI 可绿，后端/前端却没有 ADR-004 指定的唯一 DTO 产物。`ready_for_review` 与实际可消费状态不一致。
- 最小修复：使用 `"${OUT}/${name}（..."`；`EXIT` trap 先保存 `$?`、清理后以原状态退出；增加一个在临时输出目录删除整个 `python/`、整个 `typescript/` 后分别断言 exit 1 的回归测试。M0-09 入库完整产物后移除 `--allow-scaffold`。

### S07-R07 P1：浏览器 SSE 鉴权方式只写在 Markdown，OpenAPI 无法生成可用客户端

- 位置：`src/contracts/api.v1.yaml:20-21`、`:221-241`；`src/contracts/events.v1.md:19-21`。
- 触发：前端按文档用原生 `EventSource` 订阅任务。OpenAPI 的该 operation 继承全局 `bearerAuth`，但 `EventSource` 不能设置 Authorization；Markdown 又要求 `?token=` 一次性令牌，而 operation 没有 `token` 参数，契约中也没有签发该令牌的端点。
- 影响：按生成客户端或 OpenAPI 实现的后端会要求 Bearer header，按时序文档实现的前端只能发 query token，任务进度流在浏览器中无法建立；若临时复用长期 Bearer query 参数，还会把主令牌暴露到访问日志。
- 最小修复：在机器契约中增加一次性 SSE token 的签发端点和带时效/任务作用域的响应模型；给事件 operation 显式声明 query 参数/对应 security 方案并覆盖全局 bearer。补一条集成测试：普通 Bearer query 被拒，任务限定的短期 token 可连接且不能读取其他任务。

### S07-R08 P1：取消端点的响应无法表达“已请求、尚未取消”

- 位置：`src/contracts/api.v1.yaml:243-257`、`:1027-1061`；`src/contracts/events.v1.md:54-58`；`docs/decisions/ADR-006-implement-task-cancel.md:6-10`。
- 触发：运行中任务调用取消。ADR 与事件文档规定端点只置标志并立即返回，worker 到阶段边界后才进入 `cancelled`；但 200 响应描述写“已转入 cancelled”，返回的 `Task` 又没有 `cancel_requested` 字段（该字段只存在于 `TaskEvent`）。
- 影响：后端只能谎报已终止，或返回仍在运行但客户端无从判断取消已受理。前端可能提前关闭 SSE、显示完成取消，随后遗漏完成/失败竞争的实际终态。
- 最小修复：让取消响应返回可机读的 `cancel_requested` 与当前真实 `stage`（可给 `Task` 增字段或定义 `CancelTaskResponse`），把 200/202 文案改为“请求已受理”；终态调用仍返回 409，并为“worker 完成先赢/取消先赢/queued 直接取消”各加一条契约与服务测试。

### S07-R09 P2：`failed` 状态仍可省略 `error`

- 位置：`src/contracts/api.v1.yaml:1027-1055`、`:1063-1090`；文档要求见 `src/contracts/events.v1.md:33`、`:50`。
- 触发：返回 `Task(stage=failed)` 或发送 `TaskEvent(stage=failed)`，但省略 `error`。
- 实测：JSON Schema 接受 `{"task_id":"t","stage":"failed","progress":0.5}`，也接受带完整必填基础字段但无 `error` 的 `Task`。
- 影响：生成类型会把失败原因视为可选，前端拿到终态却没有错误码/说明；R05 所称的统一状态机仍只靠自然语言维持。
- 最小修复：像 `ChatResponse` 一样按状态拆分，或使用 JSON Schema `if/then` 令 `stage=failed` 时 `error` 必填且非 null；非失败状态禁止非 null `error`。补实例级正反例。

### S07-R10 P1：知识点详情允许空来源，违反页面与可追溯验收

- 位置：`src/contracts/api.v1.yaml:366-381`、`:1207-1216`；验收约束在 `specs/course-knowledge-graph.md:29-30`（条件 5）。
- 触发：详情返回 `source_refs: []`。`KnowledgePointDetail` 只把字段设为 required，没有 `minItems: 1`。
- 实测：当前 JSON Schema 接受带空 `source_refs` 的完整 `KnowledgePointDetail`。
- 影响：节点详情可以没有任何原文入口，教师审核和学生解释链断裂；这与 R03 已修复的问答引用硬约束形成不一致。
- 最小修复：给详情分支的 `source_refs` 增加 `minItems: 1`；若手工节点确实允许无文档证据，应建立显式 `manual` 分支并要求编辑日志来源，而不是用空数组含混表达。补空数组拒绝测试。

### S07-R11 P2：两个成功响应仍允许“空成功”或缺少验收字段

- 位置：`src/contracts/api.v1.yaml:1568-1579`（`RecommendResponse`）与 `:1797-1824`（`StudyMaterial`）。
- 触发：推荐接口返回 `{}`；学习材料只返回讲解和三道题，不返回示例或任何来源。
- 实测：当前 JSON Schema 接受 `{}` 作为 `RecommendResponse`；也接受缺 `examples`、缺 `source_refs` 的 `StudyMaterial`。
- 影响：生成客户端必须额外猜测响应分支；学习材料可在缺示例、缺出处时仍被当作 200 成功，违反规格的“讲解 + 示例 + 3 道题”及项目来源要求。
- 最小修复：把推荐响应拆成带判别字段的 `recommendations` / `path` 两分支并各自 required；`StudyMaterial` 要求非空 `examples` 和至少一条 `source_refs`，证据不足时定义可机读 `not_covered` 分支。补上述两个已接受负例。

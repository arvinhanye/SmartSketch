# 架构决策记录（ADR）

## ADR-001：前端采用 Vue 3 + AntV G6 的 2D 图谱

- **日期**：2026-09-22
- **背景**：当前赛题 MVP 需要稳定呈现关系、筛选和编辑；早期方案中的 3D 模式会增加渲染与交互复杂度。
- **决定**：使用 Vue 3、TypeScript、Vite 和 AntV G6，只交付 2D 图谱。
- **后果**：优先建设图谱可读性与审核体验；后续若引入 3D，作为独立规格与 ADR。

## ADR-002：Neo4j + SQLite 双存储

- **日期**：2026-09-22
- **背景**：图谱遍历/向量检索与业务任务、进度、版本的数据访问模式不同。
- **决定**：Neo4j 保存图谱与向量索引，SQLite 保存课程业务、任务、进度和版本元数据。
- **后果**：跨存储操作由服务层编排，必须记录失败状态并支持重试/补偿。

## ADR-003：可信问答以来源引用为硬契约

- **日期**：2026-09-22
- **背景**：课程问答必须可复核，不能仅依赖模型生成内容。
- **决定**：问答 API 要么返回至少一个可定位来源，要么返回 `NOT_COVERED`。
- **后果**：检索、提示词和响应 DTO 都需要来源字段；引用校验纳入测试。

- **评估方案**（A/B/C 的原始对比来自 `209be9` 的 ADR-004 首版，原样保留其否决理由，便于复核本次是否只是换个说法）：

  | A. Pydantic → OpenAPI → TS | 手写 `src/contracts/v1/python/` | 真源同时是 FastAPI 运行时校验模型，响应结构不可能偏离契约；不引入第三种语言 | `openapi.json` 要等 FastAPI 应用存在才能导出，而契约必须先于应用冻结；SSE 事件与图谱交换不在 OpenAPI paths 内，仍需单独导出 JSON Schema | 否决 |

- **为什么采纳 B′ 而不是清单默认的 Pydantic-first**（四条可核查依据）：
  1. 首版否决 B 的**唯一**理由是「后端仍需手写并手改 Pydantic」。该前提可直接消掉：Pydantic 不手写、不手改。前提消失后否决理由不成立。
  2. A 的核心优势「真源即运行时校验对象」要等 FastAPI 应用存在才能兑现，而契约必须在骨架阶段冻结（B08～B13 的依赖方 B15/C12 都要先拿到类型）。A 在当前阶段无法自洽地产出生成物。
  3. 迁移成本不对称且可量化：YAML 侧已有 22 路径 / 29 操作 / 59 schema / 189 `$ref` 并已逐行审查；`v1/python/` 一行未写。选 A 要先付一次翻译成本再重审一遍，选 B′ 成本为零。
  4. B′ 顺带解掉 A 的第二项代价：SSE 事件与图谱交换在 YAML 中就是 `components/schemas`，无需先有 Python 对象即可导出 JSON Schema。

- **决定**：
  1. **真源**：`src/contracts/api.v1.yaml`（OpenAPI 3.1），**唯一允许人工编辑的机器可读契约**。`src/contracts/errors.v1.md`、`src/contracts/events.v1.md` 是配套文档，只写 OpenAPI 表达不了的时序与语义，不重复定义结构。
  2. **生成物**：`src/contracts/v1/generated/`，含 `openapi.json`、`schemas/*.schema.json`、`python/`（Pydantic v2）、`typescript/`（`.d.ts`）。该目录内所有文件**禁止手工编辑**。
  3. **写入方**：真源由后端 Agent 单独拥有并人工编辑；生成物只由 `./scripts/gen-contracts.sh` 写。前端与后端都是**只读消费方**——后端从 `v1/generated/python/` 导入对外 DTO，`src/backend/app/schemas/` 只放不对外暴露的内部模型；前端从 `v1/generated/typescript/` 导入类型，不得在 `src/frontend/` 内重写、断言或用 `any` 绕过。
  4. **生成命令**：`./scripts/gen-contracts.sh`，`--check` 为只校验模式（重新生成后比对，不一致即非 0 退出）；同一份 YAML 生成两次必须字节一致。生成器版本锁在 `src/contracts/toolchain.txt`；缺工具必须非 0 退出，仅 `--allow-scaffold` 可降级且必须打印未完成验收标记（B07 的验收条件）。
  5. **变更顺序（硬规则）**：任何 REST / SSE / 图谱格式变更，第一步必须改 `api.v1.yaml`；同一次提交必须同时包含真源改动、重新生成的产物、受影响的规格或 ADR。生成物出现手工编辑、或 `--check` 不通过，一律拒绝合入。
  6. **不双写**：本条签收后，`v1/python/` 作为「手写真源」的方案作废；清单中指向该目录的路径按下方映射表改读为 YAML 真源 + 生成物，不得同时维护两套。

| `--check` 与真源同步 | exit 0 |
| 篡改检出（`openapi.json` / `python` / `typescript/openapi.d.ts` / `schemas/TaskEvent.schema.json` 各加一个换行） | 四项均非 0 退出，恢复后 exit 0 |
| 生成的 Pydantic 可用性 | import 成功，54 个 `BaseModel` 子类，pydantic 2.13.5 |

- **「推翻条件」第 3 条不触发**：`datamodel-code-generator` 能从本 YAML 生成可用的 Pydantic v2 模型，B′ 的前提「Pydantic 不手改」成立。ADR-004 的结论维持不变（本补注写成时仍待签收，此后已于 2026-09-22 由 ArvinHan 签收）。
- **实测暴露两个缺陷，已在 `740adb` 的 `8865686` 修复**（经用户授权直接改该分支；本仓库的 ADR 不随之改动）。**注意**：第 2 项的修复在 UTF-8 locale 下引入了新的假绿，已在 `978671e` 修复，见下方第 4 条：
  1. `gen-contracts.sh` 的 `--output "$dest/python"` 产出的是一个**没有扩展名的文件** `python`，不是 ADR-004 第 2 条写的 `python/` 目录。内容是合法 Pydantic v2，但按当前路径**无法被 import**。修法：先 `mkdir -p "$dest/python"` 再 `--output "$dest/python/models.py"`，产出内容与修复前逐字节相同，只是落点变了。
  2. `--check` 在产物**缺失**（而非内容不同）时退出码是 2 而不是 1，且「跑 gen-contracts.sh 重新生成」那行提示不会打印——`set -euo pipefail` 下第二次 `diff` 的非 0 退出会让脚本在到达 `exit 1` 前就中止。门禁仍然是红的，不是假绿，但操作者丢了修复提示。修法：把该 `diff` 裹进 `{ ... || true; }`，并为「产物缺失」单独给一条明确信息。
  3. 附带修：两处 `diff` 加 `-x __pycache__`。`python/` 变成目录后，任何人 import 过生成的模型都会在里面留下字节码缓存，那不是契约漂移。
  4. **更正（2026-09-22，Codex S07-R06）**：`8865686` 对第 2 项的修复在 **UTF-8 locale** 下引入了新的假绿。「生成物缺失」那行写成 `"$OUT/$name（…"`，macOS 自带的 bash 3.2 在 UTF-8 locale 下把全角「（」的字节并入变量名，`set -u` 中止；而 bash 3.2 进入 EXIT trap 时 `$?` 已是 0，于是缺产物时 `--check` exit 0，`verify.sh` 输出 "All verification checks passed"。上面那组验证只在 C locale 下跑过，所以漏了。已在 `740adb` 的 `978671e` 修复：变量加花括号，EXIT trap 加「没走到脚本结尾即按失败处理」的守卫，并加先红后绿的回归测试；C / en_US.UTF-8 / zh_CN.UTF-8 下缺产物均实测 exit 1。
- **仍未修（留给 B14 / M0-09）**：`--check` 只遍历本次生成出来的阶段，`v1/generated/` 顶层多出的**整个陈旧阶段目录**检不出来（阶段**内部**多出的陈旧文件能检出）。
- **`740adb` 已入库的 `v1/generated/` 不完整**：只有 `openapi.json` 与 3 个 `schemas/*.json`，缺 `python/` 与 `typescript/`（它们是在降级模式下被跳过的）。这 4 个文件与真源实测一致，但对该分支跑 `--check` 现在会非 0 退出。补齐入库是 M0-09 的动作。
- **版本漂移**：`src/contracts/toolchain.txt` 锁 `jsonschema==4.23.0`，本机校验侧解释器（conda base Python 3.13.5）装的是 4.26.0；`pyyaml` 6.0.2、`openapi-spec-validator` 0.9.0 与锁一致。是否收紧由 B07 处理。

## ADR-009：API 路径前缀、wire 枚举大小写与前置关系成环分流

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-22。本条由原子任务 **A02** 提交，关闭 PLAN-D01 的第三项「API 前缀」（前两项已由 ADR-004 关闭，PLAN-D01 至此全部关闭）。
> 规范表只有一份，在 `docs/architecture.md`「API 前缀与 wire 枚举」；成环算法与验收在 `specs/course-knowledge-graph.md`「前置关系成环处理」。本条只记录决定与理由，不复制表格。

- **日期**：2026-09-22
- **背景**：ADR-004 裁定了契约「怎么表达、谁写」，但把三处内容漂移留给 A02：
  1. **路径前缀**：S2 表 6.6 与 `ff30e0` 用 `/api/...`；`740adb` 与 ADR-004 端点迁移表用 `/api/v1/...`。
  2. **枚举大小写与遗漏**：AGENTS.md §4、ADR-003、`.claude/rules/backend.md` 写 `NOT_COVERED`，而 YAML 真源的 wire 值是 `status: "not_covered"`；main 的规格状态机缺 `persisting` 与 `cancelled`（Codex R05）；`740adb` 的 `src/contracts/README.md` 写 `not_covered_reason`，YAML 字段却是 `reason`。
  3. **前置关系成环**：S2 规则校验写「出现环时保留置信度较高的边，最弱的边降级为'相关'并进入审核」；`740adb` 的 ADR-005 却把「前置关系成环被拒」列为 `persisting` 的失败原因，按字面读就是一条模型错边让整份资料的任务失败。架构审查把它列为「自动策略与规格待对齐」。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 前缀 | `/api/v1` | **采纳** | 与真源文件名 `api.v1.yaml`、生成物目录 `v1/`、ADR-004 端点表一致，零迁移成本；主版本号有唯一可见位置 |
  | 前缀 | `/api`（S2 原样） | 否决 | 要改 ADR-004 端点表与 `740adb` 的 22 条路径；v2 时只能靠请求头区分版本 |
  | 未覆盖 | wire `not_covered` | **采纳** | 符合「只有错误码与关系类型大写」的统一规则；YAML、`events.v1.md` 与判别联合 mapping 都不用改 |
  | 未覆盖 | wire `NOT_COVERED` | 否决 | `ChatStatus` 会成为唯一大写的状态枚举，规则出现例外；需改 YAML、事件文档与 discriminator |
  | 自动成环 | 降级不失败 | **采纳** | 与 S2 一致；错边进入审核队列，教师可见可改；任务不因一条低置信度边作废 |
  | 自动成环 | 整个任务 `failed` | 否决 | 一条模型错边就让整份资料的处理作废，教师只能重跑 |
  | 自动成环 | 丢弃成环边 | 否决 | 教师看不到被丢弃的关系，违反「AI 生成、教师审核」的人机协同原则 |

- **决定**：
  1. **前缀**：所有 REST 与 SSE 端点为 `/api/v1`，唯一例外 `GET /health`。S2 的 `/api/...` 视为省略版本号的缩写。ADR-004 端点迁移表不改。
  2. **大小写规则**：UPPER_SNAKE 只用于 `ErrorCode` 与 `RelationType`；其余所有 wire 枚举值（含 SSE 事件名、判别字段取值）一律 lower_snake。
  3. **概念名与 wire 值分离**：`NOT_COVERED`、`TASK_FAILED` 是共同契约中的概念名，wire 分别是 `status: "not_covered"` + `reason`、`stage: "failed"` + `error`，都不是错误码。新代码、测试与前端分支只用 wire 值。AGENTS.md、ADR-003 与角色规则的措辞不改，由架构文档的映射表对照。
  4. **`TaskStage` 取 9 个值**：`queued`、`parsing`、`extracting`、`merging`、`persisting`、`awaiting_review`、`completed`、`failed`、`cancelled`，终态为后三者。转换触发者、取消竞争与重连语义归 A03，本条不定。
  5. **成环按来源分流**：
     - 人工编辑（新建、改类型、改端点、反转、恢复 `rejected`、合并重接边、自环）成环 → 409 `CYCLE_DETECTED` + `details.cycle`，不自动修复；
     - 自动候选成环 → 在环上未经教师确认的 `ai` 边（`status ∈ {draft, low_confidence}`）中选置信度最低者（并列取 `id` 最小），改为 `RELATED_TO` + `low_confidence` 送审核，逐环重复直到无环，任务继续到 `awaiting_review`；
     - 环上无可降级边（草稿已违反不变量）→ 任务 `failed`，`CYCLE_DETECTED`；
     - 发布时仍有环 → 409 `PUBLISH_BLOCKED`。
- **后果**：
  - `740adb` ADR-005 第 1 条中「前置关系成环被拒」作为 `persisting` 失败原因，收窄为「环上无可降级边」这一种情形。A10 导入 ADR-005 时在其文首加注指向本条，不改原文。
  - `740adb` `src/contracts/README.md` 的 `not_covered_reason` 须改为 `reason`（以 YAML 为准），随 A10 导入或 B13 修正。
  - **契约缺口**：`Relation` 没有字段记录「原为 `PREREQUISITE`、因哪条环降级」，审核队列无法向教师解释降级。B11 须先在 `api.v1.yaml` 增加字段并重新生成，F13 才能实现降级。
  - F05（DAG 纯函数）须同时提供「返回环路」与「按本条规则选出待降级边」两种能力；F06（人工写入）只用前者。
  - **ADR-008 复核**（ADR-004 编号表要求 A02 复核）：关系类型、任务状态机、枚举命名与本条一致。唯一差异是 main `docs/architecture.md` 的 Neo4j 文本块标签写 `SourceChunk`，ADR-008 写 `Chunk`。它不是 wire 枚举，本条不裁定，交 A10 导入 ADR-008 时统一。
- **推翻条件**：
  1. 评测或试用显示自动降级大量误伤真实前置关系（例如教师在审核中把降级边改回 `PREREQUISITE` 的比例很高）。此时应重开第 5 条，而不是调参数掩盖。
  2. 需要同时对外提供两个主版本时，前缀规则随 v2 的 ADR 一并重审。
- **签收**：ArvinHan 2026-09-22

## ADR-010：任务生命周期——处理完成与审核完成分离、`persisting` 不可取消、抽取部分失败按阈值

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-23。本条由原子任务 **A03** 提交，关闭 PLAN-D03 中的「取消」与「部分失败语义」；「队列 / 租约 / 重试」仍归 A06，PLAN-D03 因此**部分关闭**。
> 规范表只有一份，在 `specs/task-processing.md`（转换表、取消矩阵、失败码、SSE 关流、验收 TASK-1～22）。本条只记录决定与理由，不复制表格。
> **措辞修订（2026-09-23，Codex A03-R01/R02，决定方向不变）**：决定 1 补明任务 SSE 只覆盖处理阶段、`completed` 不经已有连接送达；决定 2 的推进谓词由「草稿已含在本次快照内」改为「T6 提交序号 ≤ 快照任务水位」，消除与「全部驳回仍转 `completed`」的矛盾。

- **日期**：2026-09-23
- **背景**：ADR-009 把 `TaskStage` 定为 9 个值、3 个终态，把转换触发者、取消竞争与重连交给 A03。现行描述（`740adb` 的 ADR-005/006 与 `events.v1.md` §2）留下这些缺口：
  1. `awaiting_review → completed` 由教师发布触发，但只有终态事件才关 SSE，于是审核期间（可能数天）连接一直空挂；一门课多份资料、多个任务，而发布按课程进行，发布推进哪些任务没有定义。
  2. 规格写「任一非终态可转 `failed` 或 `cancelled`」，`awaiting_review` 也在其中，但取消一个已处理完的任务要撤回什么没有定义。
  3. `persisting` 跨 Neo4j 与 SQLite 写草稿（ADR-002）；中途取消会留下半截图谱，ADR-006 第 5 条把清理策略推给了尚不存在的 M1-06。
  4. 抽取按块调用模型，部分块在重试后仍失败时整个任务如何处理，没有任何文档定义（架构审查「每块失败可重试，部分失败的整体状态与发布条件需定义」）。
  5. 取消端点的 200 响应写「已转入 cancelled」，而协作式取消此时通常还没生效；`Task` 也没有 `cancel_requested` 字段（Codex S07-R08）。
  6. SSE 令牌一次性、有效期 ≤60 秒，`events.v1.md` §4 却依赖 `EventSource` 自动重连，而自动重连会拿旧令牌去连。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 处理完成与审核完成 | `awaiting_review` 为处理结束态，推送后关流；发布时按任务水位推进 `awaiting_review` 任务到 `completed` | **采纳** | 连接不空挂；worker 职责在写完草稿时结束，边界清楚；不需要新端点 |
  | 同上 | 语义同上，但 SSE 保持到发布 | 否决 | 审核可持续数天，连接长期空挂；前端离开页面后也拿不到后续推送 |
  | 同上 | 教师逐份资料点「审核完成」 | 否决 | 需新端点与契约改动；审核项目前不按资料归属，实现成本最高 |
  | 部分失败 | 失败块占比 ≤ 阈值继续，超阈值失败 | **采纳** | 一次模型抖动不致整份资料作废；阈值取 0 即退化为严格模式，保留选择权 |
  | 同上 | 任一块失败即整任务失败 | 否决（可由阈值 0 实现） | 太脆弱，教师只能整份重跑 |
  | 同上 | 只要有一块成功就继续 | 否决 | 可能产出覆盖很差的草稿而教师未必留意 |
  | 取消遇到 `persisting` | `persisting` 不可取消，进入前为最后取消点 | **采纳** | 取消永远不留半截草稿，ADR-006 第 5 条由结构保证而非补偿保证；竞争由单行比较并交换确定 |
  | 同上 | 可取消并跨库补偿 | 否决 | 要实现并测试跨库补偿与补偿失败，F13 复杂度明显上升，换来的只是几秒的响应 |
  | 同上 | 受理但完成先赢 | 否决 | 前端先显示「取消中」再看到处理完成，语义不直观 |

- **决定**：
  1. **`awaiting_review` = 处理完成**：worker 不再触碰；不可取消（409 `processing_finished`）、不会转 `failed`；SSE 推送该快照后服务端关流，客户端也须关闭。任务 SSE 只覆盖处理阶段：每个连接恰好以一条结束事件（`awaiting_review` 快照或一个终态事件）收尾；`completed` 不经已有连接送达，通过任务查询或课程发布状态观察。若要实时推送发布结果，须另定课程级事件流，不得恢复处理流的长连接。
  2. **`completed` = 审核完成**：发布成功时，在切换发布指针的同一 SQLite 事务内，把该课程中 T6 提交序号 ≤ 本次快照**任务水位**的全部 `awaiting_review` 任务转为 `completed`。任务水位是建立快照时（与 `persisting` 提交串行）读取的该课程最大 T6 提交序号；谓词只看提交先后，不看任务内容是否进入快照，因此内容被全部驳回的任务同样转 `completed`。发布失败、版本回滚都不改变任务状态。
  3. **`failed` 只能从 `parsing`～`persisting` 转入**，`cancelled` 只能从 `queued`～`merging` 转入。
  4. **取消**：`queued` 由 API 直接转 `cancelled`；`parsing`/`extracting`/`merging` 置持久标志 `cancel_requested`，worker 在阶段边界及 `extracting` 的块间检查点转 `cancelled`；`merging → persisting` 是最后取消点；`persisting` 取消返回 409 `persisting_uninterruptible`。所有受理结果均为 HTTP 200 + 含真实 `stage` 与 `cancel_requested` 的 `Task` 快照；重复取消幂等；对终态取消仍 409（ADR-006 第 4 条不变）。
  5. **部分失败只在 `extracting`**：环境变量 `TASK_MAX_FAILED_CHUNK_RATIO`，默认 0.2、取值 `[0, 1)`；失败比例 ≤ 阈值继续到 `awaiting_review` 并逐块记录定位与错误码，否则 `failed`；允许结论确定后提前失败；部分失败不阻塞发布。
  6. **重连**由前端 `api/` 封装管理：出错即关闭连接、重新申领令牌再建连，退避后降级轮询；不依赖 `EventSource` 自动重连，不使用 `Last-Event-ID`。
  7. **终态不可复活**：再处理一律新建任务、分配新 `task_id`；入口形式交 C06/C07。
- **后果**：
  - **ADR-005 复核**：状态机序列与 `persisting` 阶段维持。其第 1 条「前置关系成环被拒」作为失败原因已被 ADR-009 收窄，本条不再改动。
  - **ADR-006 复核**：第 1、2、4、6 条维持。第 3 条「阶段边界检查」细化为「阶段边界 + `extracting` 块间」，仍不打断在途的单次模型调用。第 5 条「不得留下半截图谱」改由决定 4 在结构上保证：取消只可能发生在草稿写入之前；`persisting` **失败**后的清理机制归 F13/A06。第 5 条中「清理策略在 M1-06 定稿」随之作废。
  - **`740adb` `events.v1.md`**：§2 转换表由 `specs/task-processing.md` 取代；§2 顺序保证第 4 条「终态事件恰好一次」改为按连接的「每个连接恰好以一条结束事件收尾」，第 5 条增加 `awaiting_review` 关流；§4 重连改为客户端管理。该文件 §6 要求终态语义变更升 v2，但 v1 尚未进入 main、没有消费者，此时修改无迁移成本。由 B10 迁移时执行。
  - **契约缺口**（均交 B08/B10，先改 `api.v1.yaml` 再生成）：`Task.cancel_requested`、`TaskCounts.chunks_failed`、`Task.failed_chunks`、`failed ⇔ error` 约束（S07-R09）、取消端点描述、4 个提议新错误码 `DOCUMENT_UNREADABLE` / `EXTRACTION_INCOMPLETE` / `STORAGE_UNAVAILABLE` / `INTERNAL_ERROR`。新码进入真源前，`docs/architecture.md` 的 `ErrorCode` 行不改。
  - **后续约束**：A06 补写 `specs/task-processing.md` §8 时不得改变转换表与不变量；同一课程的 `persisting` 提交与发布快照必须串行，机制归 A04/A06；阈值变量登记归 A07。
- **推翻条件**：
  1. 实测中教师普遍需要在审核期间撤回整份资料的内容，而驳回/删除操作不够用——此时重开决定 1，考虑为 `awaiting_review` 定义撤回语义。

- **日期**：2026-09-23
- **背景**：ADR-010 定了任务状态机与取消语义，把以下内容留给 A06：worker 如何领取任务、崩溃后谁接管、重试几次、重跑如何不重复计费和不污染数据、`persisting` 与发布快照如何串行、中间产物留多久，以及迁移前的备份与回滚。架构审查（2026-09-22）的建议是「SQLite 任务队列起步，不预先引入 Redis/Celery」。C09 的验收已写明「两个连接争同任务只有一个成功；旧租约 token 禁止续写；到期可接管」。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 部署边界 | 同机独立 worker 进程，共用 SQLite（WAL），行级比较并交换领取 + 租约 | **采纳** | 不新增基础设施；API 重启不影响处理；多 worker 互斥与崩溃接管用同一套租约解决 |
  | 同上 | API 进程内后台任务 | 否决 | API 重启中断全部处理；多个 uvicorn worker 时仍需租约；长任务与请求争用同一事件循环 |
  | 同上 | 外部队列（Redis + RQ/Celery） | 否决 | 多一个服务与依赖；任务状态仍须记在 SQLite，队列与数据库出现两份状态 |
  | 接管后续跑 | 块级检查点：`extracting` 按块续跑，其余阶段从阶段开头重跑，`persisting` 靠确定性 ID + `MERGE` | **采纳** | 最贵的抽取调用不重做；失败块计数有处可记 |
  | 同上 | 阶段级检查点，依赖模型调用缓存省钱 | 否决 | 缓存失效时整段重新计费 |
  | 同上 | 整任务重跑 | 否决 | 一次崩溃费用与耗时翻倍；`progress` 不能回退，进度条长时间停滞 |
  | 阶段级临时故障 | 主动释放 + 延迟重排，计入同一任务尝试上限 | **采纳** | 只有一套重试机制；崩溃循环的任务被同一上限止住 |
  | 同上 | 直接失败 | 否决 | Neo4j 重启几秒就让正在入库的任务全部作废 |
  | 同上 | 进程内原地重试 | 否决 | 与崩溃接管形成两套并行计数；等待期间持有租约 |

- **决定**：
  1. **部署边界**：API 与 worker 为同一台机器上的不同进程，共用一个 SQLite 文件（WAL + `busy_timeout`）；`WORKER_PROCESSES` 默认 1，可多个。**不支持**跨机器、网络文件系统上的 SQLite、第二个队列；改变任何一项须先有新 ADR。时间比较一律用 SQLite 求值的当前时间。
  2. **领取与租约**：任务行增加 `lease_owner`、`lease_token`、`lease_expires_at`、`attempt`、`not_before`、`cleanup_pending`（内部字段，不上 wire）。领取为单条带 `RETURNING` 的条件更新，先来先领；心跳每 `L/3` 续约（`L` 默认 60 秒）；worker 的每次 SQLite 写入都带令牌条件，影响 0 行即停止；Neo4j 写入改用「离上次续约超过 `L − L/3` 不得发起外部写入」的本地截止规则。
  3. **回收**：租约过期（或已释放）的处理中任务——已请求取消的由回收者转 `cancelled`；尝试已用完的转 `failed`；其余等待接管。
  4. **三层重试**：L1 模型调用（E04）；L2 块，默认 2 次尝试，耗尽记为失败块；L3 任务，默认 3 次领取，耗尽 `failed`。阶段级临时故障只有存储不可用与模型熔断两种：主动释放并退避 30 秒 × 2^(attempt−1) 后重排；熔断期间当前块不记失败块。正常退出的释放不计尝试。原因不明的耗尽报 `TASK_ATTEMPTS_EXHAUSTED`（提议新码），已知临时故障的耗尽沿用该故障码并附 `attempts`。
  5. **幂等**：`parsing` 按确定性块 ID 覆盖写；`extracting` 按块检查点续跑；`merging` 重跑、模型结果靠 E 组的缓存；`persisting` 在课程写锁下以单个 Neo4j 事务 `MERGE` 写入、再以带令牌条件的 SQLite 事务执行 T6；最终失败按 `created_by_task` 撤销本任务新建的内容（**修订 1 改为按任务贡献撤销，失败即不可见**），清理失败置 `cleanup_pending` 由回收重试。`model_calls` 按「任务 + 块 + 用途 + 尝试序号」去重统计（**修订 2 改为按每次实际调用的 `call_id` 去重**）。
  6. **课程写锁**：`course_locks` 与任务租约同构，只在 `persisting` 的「Neo4j 写入 + T6」与发布的「建立快照 + 读取水位」两处持有；不嵌套；`merging` 不持锁，跨任务重复进入审核的「疑似重复」。
  7. **中间产物**：块检查点在终态或 `awaiting_review` 后保留 7 天；`failed`/`cancelled` 任务的来源块同批删除；已处理完成任务的来源块与 `model_calls` 永久保留。
  8. **迁移**：对任务相关表的每次迁移须停机（有未过期租约或写锁即拒绝）、先 `VACUUM INTO` 备份并通过 `integrity_check`、单事务执行；只向前，回滚 = 停机后用备份替换数据库并重启；恢复后处理中的任务按租约正常接管。
- **后果**：
  - ADR-010 的转换表与不变量不变。§1～§7 中原写「归 A06」的指针改为指向 §8 的具体小节；§6「由 A06 定」一行填为决定 4 的耗尽码。
  - **ADR-006 复核补充**：协作式取消在接管场景下的处理由决定 3 补全——worker 崩溃后已请求取消的任务不必等待重新领取，由回收者直接转 `cancelled`。
  - **A03 的「A04/A06 串行化机制」由决定 6 提供**；发布侧何时持锁仍归 A04，G04 实现前须先有 A04。
  - **契约缺口**：B08 在 `ErrorCode` 增加 `TASK_ATTEMPTS_EXHAUSTED`（与 ADR-010 的四个提议码同批）。`attempt` 暂不上 wire。
  - **实现依赖**：C01 建迁移运行器时落实决定 8 并把恢复命令写入运行手册；C09 实现决定 2、3；E04 提供熔断状态供决定 4 判断；E12 实现块检查点；E 组定模型调用缓存的键与失效；F13 实现决定 5 的 `persisting` 与清理；K08 按决定 1 编排 worker 容器（与 API 同机、共享数据卷）。

  1. 需要跨机器部署 worker，或单机吞吐不足以支撑演示与评测规模——此时重开决定 1，评估外部队列。

### ADR-011 修订 2：`model_calls` 以每次实际调用的 `call_id` 为身份，预写并估算未知用量（Codex A07-R01）

- **日期**：2026-09-23
- **背景**：Codex 审查（`docs/reviews/codex-claude-a05-a07-2026-09-23-0804z.md`）指出，A07 要求 L1 重试、备用调用与 E05 修复调用都计入预算，而决定 5 的去重键「任务 + 块 + 用途 + 尝试序号」在同一块尝试内对多次实际调用取值相同，按键去重会吞掉真实用量；问答调用没有任务 ID，键无从定义。核对后成立，且还有一处未提及：客户端断线或超时时，供应商侧已产生的用量拿不到，「收到响应才记录」的做法会让这类调用完全漏计。
- **评估方案**：

  | 方案 | 结论 | 理由 |
  | --- | --- | --- |
  | 每次实际调用一个 `call_id`，发请求前预写，未收到响应按上限估算 | **采纳** | 多次调用各计一次；断线、崩溃不漏计，估算只会偏保守；问答以 `request_id` 归属，无需任务 ID |
  | 由归属字段拼确定性复合键 | 否决 | 各代码路径须精确维护调用序号，问答需另一套键；断线漏计仍在 |
  | 只加 `call_id`，收到响应后才记录 | 否决 | 修了合并问题，但断线与崩溃仍漏计，预算仍可能低估 |

- **决定**：
  12. **调用记录**：每次实际发出的供应商调用（LLM 与向量）一条 `model_calls` 记录，身份与去重键为发请求前生成的 `call_id`。发请求前预写 `status = sent`，预写失败则不发请求；收到响应后按 `call_id` 回写真实 usage。计费量：已回写取真实 usage（无 usage 记 0；**修订 3 改为：无 usage 时生成前被拒计 0，其余按估算**）；停在 `sent` 取「输入估算 + 声明的输出上限」。原键各项降为归属字段；问答调用 `task_id` 为空、以 `request_id` 归属。E03 必须为每个 LLM 请求声明输出上限。
- **后果**：
  - `specs/task-processing.md` §8.4「计费不重复」修订；LEASE-17 修订，新增 LEASE-24～27。
  - `docs/integrations.md`「预算」的计量、软上限、任务预算、每日预算四条修订，新增「调用记录（`model_calls`）」字段表。
  - 实现依赖：E03 声明输出上限与输入估算；E04 预写、回写与预算汇总；E05 修复调用独立记录；J03/J05 问答调用带 `request_id`；C01 迁移建表时以 `call_id` 为主键。
  - 估算值可能明显高于真实用量（输出上限通常大于实际输出），断线频繁时预算会提前触顶；这是有意的保守方向。
- **签收**：ArvinHan 2026-09-23

### ADR-011 修订 3：响应缺 usage 时按估算计费，生成前被拒的错误计 0（Codex FIX-R01）

- **日期**：2026-09-23
- **背景**：Codex 复审（`docs/reviews/codex-claude-a04-fixes-1012b6f-2026-09-23-1215z.md`，主目录，尚未入库）指出，修订 2 只在「未收到响应、停在 `sent`」时采用估算，收到响应但不带 usage 的调用回写后按 0 计。核对后成立：部分 OpenAI 兼容供应商在流式响应中默认不返回 usage；在备用、修复调用或兼容性不稳定的供应商上，真实发生的调用会从任务与每日预算中消失，软上限可被绕过。`call_id` 解决了去重，但没有保证计量下界。
- **评估方案**：

  | 方案 | 结论 | 理由 |
  | --- | --- | --- |
  | 缺 usage 时按错误类型区分：生成前被拒计 0，其余按估算 | **采纳** | 已经或可能已经发生生成的调用都有计量下界；生成前被拒的请求供应商不收费，且本身有界（鉴权、参数错误不重试，`429` 重试有上限），不会在限流或故障期间把预算提前耗尽 |
  | 缺 usage 一律按估算（报告的最小修复） | 否决 | 任务预算跨尝试累计、不清零；限流期间每次 `429` 都按输出上限扣减，会把一次可用性故障变成任务因预算失败 |
  | 成功响应按本地计数实际输出 | 暂不采纳 | 比输出上限更贴近真实用量，但要求 E03 对输出也实现只偏大的估算。先靠 E03 在流式请求中请求 usage 减少缺 usage 的情形，实测估算偏差过大时再考虑 |

- **决定**：
  13. **缺 usage 的计费**：响应带可解析的 usage 时按 usage 计（错误响应亦然）。响应不带 usage 时：HTTP `400`、`401`、`403`、`404`、`413`、`422`、`429`（生成前被拒）计 0；其余，即成功响应、`408`、`5xx`、流中途断开、响应无法解析，与未收到响应相同，按「输入估算 + 声明的输出上限」计入并标记为估算。`usage_estimated` 改为派生自「usage 为空且不属于生成前被拒」。E03 负责把错误归入「生成前被拒」类，并在流式请求中请求 usage（`stream_options.include_usage`）；供应商是否返回 usage 在 D-02a/b 签收时注明。
- **后果**：
  - `docs/integrations.md`：「预算」计量条，「调用记录」第 2、4 条与新增第 5 条，字段表三行，计费量一行，D-02a/b 两行。
  - `specs/task-processing.md` §8.4「计费不重复」补一句；新增 LEASE-28～30。

> **修订 3（2026-09-24 签收）**：落实 ADR-014 修订 1 决定 9、10 交给本条的两项：快照节点的合并谱系 `merged_from`，以及版本提交事务从共享序列取提交序号，见本条末尾「修订 3」；决定 2、3、4、5 的快照与提交以修订 3 为准。
> 编号说明：ADR-010（A03，PR #5）与 ADR-011（A06，PR #6）已在未合入 main 的分支上签收，本条取 012，避免 A10 导入时撞号。
> 规范文本只有一份，在 `specs/teacher-review-publish.md`「图谱版本与跨库发布协议」V1～V11；架构结论在 `docs/architecture.md`「图谱版本与跨库发布」。本条只记录决定与理由。

- **日期**：2026-09-23
- **背景**：
  1. S2 只给了 SQLite 表 `snapshots(id, course_id, version, graph_json, created_at)`。学生端的推荐要在 Neo4j 遍历前置关系，问答要在 Neo4j 做向量检索，只有 SQLite JSON 不够。
  2. SQLite 与 Neo4j 之间没有跨库事务（ADR-002），发布必须有显式提交点与补偿。
  3. `740adb` 的草稿桩把快照形态、回滚是否产生新号、重复发布、并发发布都列为「待细化」；契约用整数 `version`。
  4. A03（ADR-010）要求发布在持锁区段内读任务水位，并在切指针的同一 SQLite 事务推进 T7；A06（ADR-011）定义了 SQLite 课程写锁，并把「发布方何时持锁」交给 A04。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 存储 | 1. SQLite 快照为真相 + Neo4j 按版本物化副本 | **采纳** | 唯一同时满足「学生不读半成品」「请求中途版本不漂移」「SQLite 备份可恢复历史」；提交点只有 SQLite 中的一次 CAS；回滚可在 Neo4j 内复制，不依赖模型调用 |
  | 存储 | 2. 只在 Neo4j 存版本副本，SQLite 只存元数据 | 否决 | 放弃 S2 的 `graph_json`；Neo4j 丢失即失去全部历史，导出与审计依赖 Neo4j 在线 |
  | 存储 | 3. SQLite 存全部历史 + Neo4j A/B 两槽蓝绿切换 | 否决 | 回滚要么把向量塞进 JSON，要么重调模型；槽位复用时，仍绑定旧槽的长请求会读到正在覆盖的数据 |
  | 回滚编号 | 前滚为新版本号 | **采纳** | 版本号只增不减，当前版本恒为最大号；进度与问答日志不会出现倒序 |
  | 回滚编号 | 指针移回旧版本 / 由教师二选一 | 否决 | 前者使「当前版本」不再是最大号，下一次编号需额外约定；后者接口与测试组合翻倍 |
  | 重复发布 | 摘要等于当前发布版 → 幂等 | **采纳** | 不堆积内容相同的版本，学生端不被无意义切换；只与当前发布版比较，回滚前滚不受影响 |
  | 重复发布 | 照常产生新版本 / 409 拒绝 | 否决 | 前者历史中出现重复版本；后者违反草稿桩验收 12「不得报错」 |
  | 回滚与草稿 | 草稿不动 | **采纳** | 不丢未发布的修订；回滚只做一件事 |
  | 回滚与草稿 | 草稿重置为目标版本 / 参数选择 | 否决 | 前者覆盖未发布修改，还需另定锁节点处理；后者组合翻倍 |
  | 并发 | 课程级互斥，建快照期间暂停草稿写入 | **采纳** | 发布读到的草稿是一致状态；MVP 规模下暂停只有几秒 |
  | 并发 | 只做修订号前后比对 / 发布改为异步任务 | 否决 | 前者在编辑频繁时发布反复中止；后者要改同步契约，并依赖 worker |
  | 低置信度 | 排除 `low_confidence`，连带排除悬空边 | **采纳** | 学生看到的都是未被标为存疑的内容，教师不必一次清空队列；只删边不产生新环 |
  | 低置信度 | 全部发布 / 有存疑项即拒绝 | 否决 | 前者把降级边与存疑关系推给学生；后者首次发布门槛过高 |

- **决定**：
  1. **标识**：内部 `version_id` 为 ULID，每次发布或回滚开始时生成，永不复用；对外整数 `version` 按课程在提交时分配 `max+1`，失败尝试不占号。草稿在 Neo4j 中的 `version_id` 为保留值 `"draft"`。
  2. **存储**：SQLite `GraphVersion` 保存规范化快照与 sha256 摘要，是版本内容的真相；Neo4j 以 `(course_id, version_id)` 物化知识点、关系与章节副本，知识点向量随版本复制；文本块不可变、各版本共享，读取时按版本的资料清单过滤（**修订 1 改为按资料修订列表过滤**）。MVP 不回收已提交版本。
  3. **快照内容**：只含学生可见的内容字段与资料清单；不含审核状态、置信度、锁、来源类别、修订号、时间戳、向量与可推导字段。`low_confidence` 与 `rejected` 项及因此悬空的边被排除；疑似重复与孤立节点照常纳入。
  4. **发布**：同课程至多一个进行中的发布或回滚（部分唯一索引，否则 409 `PUBLISH_IN_PROGRESS`）→ 持课程写锁读修订号、任务水位、发布集合与向量后释放 → 校验（环、悬空端点、无效来源、空图 → 409 `PUBLISH_BLOCKED`）→ 摘要等于当前发布版则幂等返回 `unchanged: true` → 写快照 → Neo4j 单事务物化 → 读回核对摘要 → **唯一提交点**：一个 SQLite 事务内 CAS 切换指针、分配版本号、执行 T7。提交前任何失败执行补偿 C1：先以条件更新把尝试记为 `failed`，再删除该 `version_id` 的 Neo4j 副本；指针从不改变。
  5. **回滚**：以目标版本内容前滚为新版本号，向量在 Neo4j 内复制、不调用模型；目标摘要等于当前发布版则幂等；不改草稿、不执行 T7；课程状态按草稿摘要是否等于新版本判定。
  6. **课程写锁（修订 ADR-011 决定 6）**：A06 的 `course_locks` 由「`persisting` 与发布建快照两处持有」扩大为**所有草稿写入**都持有：教师编辑在持锁后、写 Neo4j 前把 `courses.draft_revision` 加 1。发布只在读草稿期间持锁，回滚只在读草稿摘要期间持锁。API 侧持锁者有界等待 `COURSE_LOCK_WAIT_SECONDS`，超时 409 `COURSE_BUSY`；worker 的等锁方式不变。
  7. **课程状态**：不单独存储，由 `published_version_id`、`draft_revision`、`published_from_revision` 推导。
  8. **读取绑定**：学生请求开始时读一次发布指针，全程使用同一 `version_id`；教师与学生都可按 `?version=` 读取已提交版本；草稿只有教师可读。
- **后果**：
  - 契约缺口：B08 新增错误码 `PUBLISH_IN_PROGRESS`、`COURSE_BUSY`；B11 给 `PublishResult` 加 `unchanged`、`excluded`，给 `GraphVersion` 加 `kind`、`source_version`，回滚端点补 409，定 `PUBLISH_BLOCKED` 的 `details.reasons` 结构。
  - A07 登记 `PUBLISH_LEASE_SECONDS`（默认 60）与 `COURSE_LOCK_WAIT_SECONDS`（默认 5）。
  - `specs/task-processing.md` §8.5「只有两处持锁」旁与 ADR-011 引言已加注指向本条（随 A03/A06 同批合入 main 时完成）；G02 的 `preparing/ready` 两态改为 `preparing/materialized/committed/failed`。
  - Neo4j 存储随已提交版本数线性增长。MVP 规模（每门课数百知识点）可接受；回收须另立 ADR，且保留期长于最长请求、不得回收当前指针。
  - 教师编辑在发布建快照的几秒内可能收到 `COURSE_BUSY`，前端需要提供重试提示。
  - 向量检索采用「多取再过滤」，召回是否足够由 J01 实测；达不到时再评估 Neo4j 过滤向量检索等方案，须回到本条。
- **推翻条件**：
  1. Neo4j 中版本副本的体量或物化耗时超出发布性能目标（例如单次物化超过课程写锁或尝试租约可承受的时长），需要重新比较方案 3 或引入增量物化。
  2. J01 实测「多取再过滤」召回明显不足，且无法靠加大取数解决。
  3. 产品要求多份草稿并行修订，本条「一份草稿 + 课程写锁」的模型不再成立。

### ADR-012 修订 1：文本块按资料修订固定、向量空间离线切换（Codex A04-R01/R02）

- **日期**：2026-09-23
- **背景**：Codex 审查（`docs/reviews/codex-claude-a04-4b2ccb5-2026-09-23-0730z.md`）指出两处问题，核对后均成立，且根因比报告更深：
  1. **A04-R01（P1）**：A06 的块 ID 为「文档 ID + 解析器版本 + 块序号」，不含内容。同一资料换内容再处理会**原地覆盖**已发布版本引用的原文；换解析器再处理会产生新块，而版本只按 `material_id` 过滤，会检索到它们；失败任务按 A06 §8.6 删除来源块时，又可能删掉处理同一内容的已发布块。
  2. **A04-R02（P2）**：查询向量总按当前模型计算，换模型后旧空间的向量（含当前发布版与共享文本块）一律无法检索；「幂等发布保留旧向量」「回滚按当前配置被拒」只是其表现。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 版本固定文本块 | 按资料修订固定（快照列修订，检索按 `revision_id` 过滤） | **采纳** | 快照只多十几个修订；过滤值少，查询快；修订与块 ID 同源，天然不可变 |
  | 同上 | 快照直接列全部 `chunk_id` | 否决 | 快照大一两个数量级；检索要带数千 ID 过滤或为每个版本建成员边，存储随版本数增长 |
  | 换向量空间 | 离线全量重新向量化 + 启动门禁 | **采纳** | 运行时只有一个空间，幂等与回滚规则无需分支；「可回滚任一已提交版本」不变；按文本哈希去重，MVP 规模代价小 |
  | 同上 | 只迁移草稿与当前发布版 | 否决 | 旧版本回滚变成有条件的，规格与前端多一种状态 |
  | 同上 | 发布或回滚时按需补算 | 否决 | 同步请求内调用模型、计费、可能部分失败；数千块的补算超出发布租约与请求时长 |

- **决定**：
  9. **资料修订与文本块不可变**：资料修订 = `(material_id, 内容哈希, 解析器版本)`，确定性生成 `revision_id`；块 ID = `revision_id` + 块序号（修订 ADR-011 决定 5 中 `parsing` 的块 ID 公式）。块一经写入不可变，写入已存在 ID 时内容哈希不一致即拒绝。失败或取消任务的来源块，其修订若属于任何已到 `awaiting_review` / `completed` 的任务或任何已提交版本，则保留（修订 ADR-011 决定 7）。
  10. **版本固定修订**：快照的 `materials` 改为 `revisions`，含任务水位以内、已进入审核的任务所产生的全部修订，纳入摘要；`invalid_source_ref` 与问答检索都按 `revision_id` 判定，不按 `material_id`。尚无实现，直接修订快照格式 1。
  11. **单一向量空间**：向量空间 = `EMBEDDING_MODEL` + `EMBEDDING_DIMENSIONS`。SQLite 记录当前空间，版本行记录 `embedding_space`。API 与 worker 启动时配置空间与记录空间不一致即拒绝启动。换空间只能停机运行离线重新向量化：新空间属性与索引与旧空间并存，算完全部文本块、草稿知识点与全部已提交版本的知识点副本并核对后（**修订 2：目标按 Neo4j 实际存量枚举并按存量核对，缓存与中间产物中的向量带空间标识**），在一个 SQLite 事务内切换当前空间与全部版本行，之后再清理旧空间；切换前任何失败旧空间完好、可重跑。向量是派生数据，重算不产生新的内容版本。
  12. **发布与回滚的空间核对**：幂等路径（P7、R3）要求摘要相等**且**空间相同；P9、R5 核对版本自身的 `embedding_space` 与当前空间。正常运行中由启动门禁保证成立，不成立即按不变式破坏 5xx 告警。
- **后果**：
  - `specs/task-processing.md` §8.4 `parsing` 行与 §8.6 删除规则已改正文并加注；ADR-011 引言加注指向本修订。
  - `docs/integrations.md` 两处「重新向量化并生成新向量版本」改为指向 V12。
  - 语义后果：资料换内容后，旧修订只要仍在发布集合范围内，新旧两份原文都可被检索；「下线旧修订」交 C06/C07，列入规格「待细化」。
  - 实现依赖：B06 启动门禁；D09/D10 按修订生成块 ID 并做不可变检查；C09/D11 的块删除保护；E07 按文本哈希缓存向量（**修订 2 改为按「空间标识 + 文本哈希」**）；F03 允许新旧空间属性与索引并存；重新向量化命令的归属任务由 A10 在清单中补登（当前清单无对应叶子任务）。
  - 验收新增 PUB-28～34。

### ADR-012 修订 2：重新向量化按实际存量迁移与核对，空间标识随向量走（Codex FIX-R02）

- **日期**：2026-09-23
- **背景**：Codex 复审（`docs/reviews/codex-claude-a04-fixes-1012b6f-2026-09-23-1215z.md`，主目录，尚未入库）指出，V12 第 3 步只重算「已到 `awaiting_review` / `completed` 的任务所产生的修订」的文本块，而不变式声明**所有**文本块都在当前空间。迁移前已排队、中断或失败的任务解析出的块（失败任务的块在回收前保留，中断任务的块在接管时复用）只有旧空间向量；切换后新空间索引检索不全，而启动门禁只比对 SQLite 记录的空间标识，发现不了。核对后成立。另有两处报告未提及：
  1. E07 按文本哈希缓存向量（修订 1 的实现依赖），键中没有空间；切换后同一段文字会命中旧空间的缓存，把旧向量写进新索引。
  2. F 组写入前只比对 Neo4j 索引维度；两个模型维度相同时，旧空间的向量（来自缓存或中断任务的中间产物）能通过核对。
- **评估方案**：

  | 方案 | 结论 | 理由 |
  | --- | --- | --- |
  | 按 Neo4j 实际存量全部重算、按存量核对；空间标识随向量写入缓存与中间产物 | **采纳** | 不变式按存量直接成立，不依赖任务状态推导；中断任务可以留在队列里，切换后接管也不会用到旧向量；多算的只是少量待回收的失败块 |
  | 迁移前排空任务队列、先回收失败任务的块，目标仍按任务状态推导 | 否决 | 运维上要先等待或取消全部任务；推导出的集合仍可能因回收延迟或实现缺陷与存量不一致，核对发现不了；缓存问题照样要修 |

- **决定**：
  13. **按存量迁移与核对**：重新向量化的目标是 Neo4j 中实际存储的全部文本块（不论所属任务状态）、全部草稿知识点（不论可见性）与全部已提交版本的知识点副本，按存量枚举，不从任务状态推导；第 4 步核对三类节点中缺新空间向量或维度不符的数量为 0，否则不切换。

### ADR-012 修订 3：快照节点的合并谱系 `merged_from` 与共享提交序号（ADR-014 决定 9、10 交办）

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-24。起草：Claude；签收时未改动决定 15～25。

- **日期**：2026-09-24
- **背景**：
  1. ADR-014 修订 1 决定 10 定下「谱系作为发布快照节点的 `merged_from` 字段保存」，把字段形状（链式来源与直接父子关系如何表示）与摘要纳入方式交给本条的下一次修订。
  2. 同条决定 9 规定：写入序号与提交序号取自 SQLite 中**同一个单调序列**，分别在进度写入事务和版本提交事务内取号。本条决定 4 的提交事务（V5 P11）目前没有取号步骤。
  3. `specs/learning-path.md` §5 的归属规则：来源归属到链上**最近的仍在绑定版本中的节点**；整条链都不在版本中时来源为 dormant；每个来源至多对应一个主节点且无环。起算版本 `k` 要从绑定版本逐个往前检查「`m` 是否连续归属到 `p`」。
  4. B11（契约）、F10（合并）、G01（快照与摘要）、G02（版本元数据）、G04/G06（提交与回滚）、I01（进度仓储）都等本条，B11 下游间接依赖约 75 个叶子任务。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 谱系形状 | 1. 节点字段 `merged_from` = 本版本中归属到该节点的**全部**来源（链已展平） | **采纳** | 读时一步得到归属，不用解析链；判定 `k` 只需逐版本查「`m ∈ p.merged_from`」；回滚复制快照时自然回退。「最近可见节点」规则由构造保证：来源一经合并就从草稿删除，中间节点在版本中时它自己尚未被合并，不会出现在更远节点的集合里 |
  | 谱系形状 | 2. 只存直接父子（`merged_from` = 直接并入者） | 否决 | 中间节点不在版本中时链就断了（`a→b→c` 发布后 `b` 已不在快照），读时要回看历史快照或另建课程级表才能接上 |
  | 谱系形状 | 3. 快照顶层数组 `lineage: [{merged_id, primary_id}]` | 否决 | 同样只能表达直接边，读时还要再做链解析与冲突检查 |
  | 是否上 wire | 1. 只存在于快照与已发布副本，不进 `KnowledgePoint` DTO | **采纳** | 学生通过进度接口的 `inherited_from[]` 看到效果；教师的「合并自」信息已在 `aliases` 与 F12 审计日志里；以后需要可作为可选字段追加（非破坏性） |
  | 是否上 wire | 2. `KnowledgePoint` 加 `merged_from` | 否决 | MVP 没有消费者，还要决定草稿与已发布两种读路径的语义 |
  | 共享序列 | 1. 全库单行计数器，在写事务内取号 | **采纳** | SQLite 只有一个写者，事务内取号即按提交顺序严格单调，回滚的事务不留号；随 SQLite 备份一起恢复，不会与数据错位 |
  | 共享序列 | 2. 每课程一行计数器 | 否决 | 也可行，但要按课程建行、迁移时补齐；决定 9 只比较同课程的序号，全局单调已经蕴含课程内单调 |
  | 共享序列 | 3. 自增日志表（每次取号插一行） | 否决 | 每次进度写入多一行没有用途的日志 |
  | 共享序列 | 4. `committed_at` / `updated_at` 等时间戳 | 否决 | ADR-014 修订 1 决定 9 已明确禁止 |

- **决定**（接续本条决定 1～14）：
  15. **字段**：快照格式中每个知识点都有 `merged_from`，为 `kp_id` 数组，集合语义。含义：**在本版本中归属到该节点的全部合并来源，链已展平**。例：`a` 并入 `b`、`b` 再并入 `c` 后发布，`c.merged_from = ["a", "b"]`。直接父子关系不进快照，只记在 F12 的图编辑审计日志中。
  16. **不变式**：同一快照内，(a) 来源不是本快照的节点；(b) 一个来源至多出现在一个节点的 `merged_from` 中；(c) 节点的 `merged_from` 不含它自己。P6 校验时违反任一条 → 409 `PUBLISH_BLOCKED`，`details.reasons[].kind = invalid_lineage`（与 `dangling_endpoint` 同属草稿不变量被破坏，只可能是实现缺陷）。读取已提交版时违反 → 按 `specs/learning-path.md` §1 的已提交版完整性错误处理。
  17. **草稿中的维护（F10、F09）**：谱系随草稿知识点保存在 `merged_from` 属性上。
      - 合并 `m → p`：`p.merged_from ← p.merged_from ∪ {m} ∪ m.merged_from`，随后 `m` 从草稿删除。
      - 删除 `p`：`p.merged_from` 随之丢弃，这些来源在之后的版本中不再归属任何节点（dormant，LP-19）。
      - 改名、改属性、改边不影响 `merged_from`。回滚不改草稿（决定 5），所以草稿谱系不随回滚回退；**版本谱系**随快照回退，再次发布时由草稿重新写入，`k` 从新版本起算（LP-20）。
  18. **发布集合**：`merged_from` 随节点原样进入快照。节点因 `low_confidence` / `rejected` 被排除时，它的 `merged_from` 一并不进入本版本，这些来源在本版本中为 dormant。
  19. **摘要与格式**：`merged_from` 按 V3「集合语义的数组」规则去重、升序后纳入规范化与摘要；没有来源时写空数组 `[]`，不省略键。尚无任何实现，与修订 1 同理，直接修订格式 1，`snapshot_format` 不升号。P8 把它物化为已发布知识点的属性，P9 复算摘要时包含它；回滚（R5）按副本复制。
  20. **快照字段清单的例外**：V3「只含学生可见的内容字段」增加一个例外——`merged_from` 不是学生可见字段，而是为进度投影随版本保存的元数据；它不进入 `KnowledgePoint` wire DTO（B11 不加此字段）。
  21. **读取**：进度投影按绑定 `version_id` 读取 SQLite 快照中的 `merged_from`（快照是真相，Neo4j 副本只供核对与图查询）。已提交快照不可变，可按 `version_id` 缓存；计算起算版本 `k` 读取本课程各已提交版本的 `merged_from` 与提交序号。
  22. **共享序列**：SQLite 单行表 `commit_sequence(singleton INTEGER PRIMARY KEY CHECK (singleton = 1), value INTEGER NOT NULL CHECK (value >= 0))`，建表的迁移同时插入 `(1, 0)`。取号只在写事务内执行 `UPDATE commit_sequence SET value = value + 1 WHERE singleton = 1 RETURNING value`，全库一个序列，不分课程。
  23. **提交序号**：版本行增加 `commit_seq`（提交前为 NULL，非空时唯一）。P11 第 1 条在同一事务内取号写入；回滚的 R7 沿用 P11 第 1、2 条，同样取号。幂等路径、C1 补偿与失败尝试都不取号。由于 `version` 与 `commit_seq` 在同一事务内分配，同一课程内版本号越大，提交序号越大。
  24. **写入序号**：进度行增加 `write_seq`，在进度写入事务内取号；同值写入判定为无操作时不取号（ADR-014 修订 1 决定 9 补注，A08S-R01）。
  25. **迁移归属**：`commit_sequence` 由 G02 与 I01 中先实现者的迁移创建，另一方只加自己的列；迁移编号按 C01 的三位版本规则在任务板预留，避免并行任务撞号。A03 的 T6 提交序号（任务水位）不受本条影响，实现时可复用本计数器，但本条不作要求。
- **后果**：
  - `specs/teacher-review-publish.md`：V2 增加 `commit_seq` 与 `commit_sequence`；V3 快照格式、发布集合、校验表与规范化规则加入 `merged_from`；V5 P11、V6 R7 写明取号；V10 增加本条交办事项。
  - `specs/learning-path.md` §7 细则 1、2 改为指向本条。
  - 任务交办：
    - **B11**：`PUBLISH_BLOCKED` 的 `details.reasons` 增加 `invalid_lineage`；`KnowledgePoint` 不加 `merged_from`；`GraphVersion` 不暴露 `commit_seq`。连同 A02-R01（`Relation.required` 补 `status`、`source`、`source_refs`）一并完成。
    - **F10**：合并时按决定 17 维护草稿 `merged_from`，并在 F12 审计日志记录直接父子关系。**F09**：删除时丢弃 `merged_from`。
    - **G01**：快照与摘要包含 `merged_from`；按决定 16 校验。**G02**：`commit_seq` 列（以及按决定 25 可能由它建的 `commit_sequence`）。**G03**：P8 物化、P9 复算包含 `merged_from`。**G04 / G06**：P11 / R7 取号。
    - **I01**：进度行 `write_seq`；**I02**：写入与同值判定按决定 24；**I05**：投影按决定 21 读取。
  - 快照体量随合并链增长，MVP 规模（每门课数百知识点）可忽略。
  - K10 备份恢复：计数器与版本、进度同在 SQLite，同一份备份内三者一致；两库时间点对齐的要求不变。
- **推翻条件**：
  1. 产品要求教师或学生在界面上看到合并链，而 `aliases` 与审计日志不够用时，追加 wire 字段或审计视图。

  | 登录方式 | 纯演示角色（点按钮进入，无口令） | 否决 | 任何人都能成为教师；需改 `LoginRequest` 契约；课程隔离的演示失去说服力 |
  | 登录方式 | 本地账号 + 演示模式一键填充 | 否决 | 在采纳方案上多一个前端开关和配置项，演示收益小 |
  | 角色粒度 | 账号类型 + 课程内角色 | **采纳** | 满足 C02；与 S2 两张表一致；课程内授权每次回查成员表，移出课程或停用账号立即生效 |
  | 角色粒度 | 仅全局角色 | 否决 | 需改写 C02 验收；教师无法在他人课程里以学生身份旁听，助教类场景日后难以扩展 |
  | 学生入课 | 教师按用户名添加 | **采纳** | 课程隔离语义清楚，`COURSE_FORBIDDEN` 对学生也有意义；只需三个成员操作和一个小页面 |
  | 学生入课 | 选课码自助加入 | 否决 | 多出选课码生成、轮换与防暴力猜测的规则，超出 MVP |
  | 学生入课 | 已发布课程对所有学生开放 | 否决 | 学生侧没有「成员」概念，多课程隔离只剩草稿可言 |
  | 学生入课 | 只由种子脚本写入成员 | 否决 | 教师无法在界面管理学生，演示与真实使用都不便 |
  | SSE 鉴权 | 不透明一次性票据存 SQLite | **采纳** | 真正一次性；API 多进程也成立；实现只需一张表和一条条件更新 |
  | SSE 鉴权 | 限定任务的短时效 JWT | 否决 | 无状态，有效期内可重放，达不到 `events.v1.md` 要求的一次性 |
  | SSE 鉴权 | 改用 Cookie 鉴权 | 否决 | 引入第二套鉴权与 CSRF 防护，偏离契约的 Bearer 方案 |

- **决定**：
  1. **登录**：本地账号，用户名 + 口令，口令慢哈希存储；登录成功签发 HS256 JWT（`sub`、`role`、`iat`、`exp`），默认有效期 8 小时，无刷新令牌，注销由前端丢弃令牌完成。没有注册端点；账号由命令行管理，演示账号由幂等种子脚本创建，口令只从环境变量 `SEED_DEMO_PASSWORD` 读取。登录失败统一 401，同一用户名连续失败 5 次后 60 秒内返回 429。
  2. **身份唯一来源**：调用者身份只来自已验证的访问令牌（或已核销的事件票据）。服务端每次请求按 `sub` 回查用户，已停用即 401。请求体、查询参数、路径、自定义请求头中的任何 `user_id` 或角色都不得用来确定调用者；作用于本人数据的请求体不含 `user_id`。
  3. **两层角色**：`users.role` 是账号类型，只决定默认首页和能否新建课程；课程内一切授权只看 `course_members.role`，每次请求回查。令牌里的 `role` 仅作前端路由提示，服务端不据此授权。学生账号只能做学生成员；教师账号可以在别的课程做学生成员。
  4. **成员管理**：新建课程时创建者在同一事务成为教师成员；`courses.teacher_id` 只用于展示。教师成员按用户名添加学生（已是成员则幂等返回、不改角色），只能移除学生成员；协作教师 MVP 只由命令行管理。学生被移除后数据保留，重新加入恢复。
  5. **授权判定与错误语义**：身份 → 定位课程 → 成员关系 → 课程内角色 → 发布状态 → 子资源作用域，先失败者决定响应。路径带 `cid` 的非成员（含课程不存在）→ 403 `COURSE_FORBIDDEN`；按 `tid` 定位的非成员 → 404 `NOT_FOUND`，不回任务快照；角色不符 → 403 `ROLE_FORBIDDEN`；学生访问从未发布的课程 → 404 `GRAPH_NOT_PUBLISHED`。不新增错误码。
  6. **访问矩阵**：教学资料、任务、图谱编辑、审核、发布与版本、成员管理仅教师成员；进度、推荐、问答仅学生成员，**教师成员不开放**；图谱与知识点读取两者皆可，学生只读已发布版本。学生的课程列表只含曾经发布过的课程，每项带 `my_role`。
  7. **SSE 票据**：`POST /api/v1/tasks/{tid}/event-ticket` 用 Bearer 申领，返回 ≥128 位随机票据，60 秒有效，库中只存哈希；`GET .../events?ticket=` 覆盖全局 Bearer，用一条条件更新原子核销，核销后重新校验账号与成员关系再开流。常规访问令牌永不进 URL。
- **后果**：

## ADR-014：推荐评分的中心度分母取 N−1；知识点合并后按合并来源继承进度

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-23。两项决定由 ArvinHan 在审查 Codex A08 后的会话中选定（审查报告 `docs/reviews/claude-codex-a08-2026-09-23.md` 的 A08-R02、A08-R03），书面条文由 Claude 记录。
> **修订 1（本条末尾，A08 §7 签收，2026-09-23 签收）**：签收 A08 §7 的缺失中性值、权重来源、推荐上限与进度接口字段，以及本条“后果”交给 A08 的两项细则。决定 2 的“取最高”增加显式写入覆盖规则（决定 9），谱系存放在发布快照中（决定 10）。
> 规范文本归 A08 的 `specs/learning-path.md`。该文件由 Codex 持有，尚未提交；本条只记录决定与理由，公式与验收由 A08 修复时写入规格，本条不代改。
> **编号说明**：main 上 ADR-009～013 已用，ADR-005～008 由 ADR-004 保留给 `209be9`、`ff30e0` 待导入的条目；本条取 014。A08 修复时直接引用本条，不再另起编号。

- **日期**：2026-09-23
- **背景**：
  1. S2 §6.4.7 只写了“重要度与图中心度加权”。A08 草案给出 `centrality(k) = (in_degree + out_degree) / (2×(N−1))`。在去重后的 DAG 中，任意两点之间至多一条边，否则就构成二元环，所以 `in+out ≤ N−1`，这个中心度恒 ≤ 0.5。审查用参考脚本确认：星形中心点在 N=2..50 时都是 0.5，3000 个随机 DAG 的最大值也是 0.5。结果是重要度的值域只有 `[0, 0.75]`，与“各占一半”的本意不符。
  2. A08 草案规定知识点合并后，被合并点的进度作废，不转给主节点。但候选真源 `kp/merge` 的语义是“被合并节点的名称并入 `aliases`，关系与来源取并集后迁移到主节点”，即认定两者是同一概念。按草案，学生已掌握的被合并点作废，主节点仍未掌握，而迁移过来的后继从“可学”变成“未解锁”：只要教师清理重复节点，学生进度就会倒退。
  3. 候选真源的 `MergeRequest{primary_id, merged_ids}` 规定主节点沿用自己的 `kp_id`；A04（ADR-012）保证 `kp_id` 跨版本不变。继承因此有稳定的落点。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 中心度 | 1. `(in+out)/(N−1)` | **采纳** | DAG 中恰好落在 `[0,1]`，星形中心点为 1；公式简单，可在单一版本上确定地计算 |
  | 中心度 | 2. 按本版本最大度数归一化 | 否决 | 稀疏图也能拉满，但多一条零分母规则，而且分值会随无关节点的度数变化 |
  | 中心度 | 3. 维持 `2(N−1)` | 否决 | 恒 ≤ 0.5，名义上的拆分比例失真 |
  | 合并进度 | 1. 按合并来源继承 | **采纳** | 与“同一概念”的合并语义一致；教师清理重复节点不会让学生进度倒退 |
  | 合并进度 | 2. 被合并点的进度作废（A08 草案） | 否决 | 合并后学生可见的进度倒退，而合并正是审核队列里的常规操作 |

- **决定**：
  1. **中心度**：`centrality(k) = (in_degree(k) + out_degree(k)) / (N−1)`。只计去重后的 `PREREQUISITE` 边，覆盖绑定版本的全图，与学生掌握集合无关。`N ≤ 1` 时为 0。重要度 `i(k) = 0.5 × importance(k) + 0.5 × centrality(k)`，其中 0.5/0.5 拆分沿用 A08 提案，签收时未改动。
  2. **合并后按来源继承进度**：知识点 `m` 合并进主节点 `p` 后，只要 `m` 不在请求绑定的版本中，学生在 `p` 上的有效状态就取 `p` 自身记录与各合并来源记录中的最高者，顺序为 `unknown < learning < mastered`。合并链沿谱系传递：`a` 并入 `b`、`b` 再并入 `c`，`c` 同时继承 `a` 与 `b`。
  3. **读时投影，不改写进度行**：继承只在把进度投影到绑定版本时计算，SQLite 中的进度行保持学生写入的原样。A08 §2 的不变量“掌握集合是学生声明的事实，不由服务修改”仍然成立，回滚也不需要撤销任何写入。
  4. **来源重新出现时不继承**：回滚等操作使 `m` 重新出现在绑定版本中时，`m` 用它自己的记录，`p` 不再从它继承。
- **后果**：
  - **A08 修复**（Codex，`specs/learning-path.md`）：
    - §3 中心度一行按决定 1 修改；补验收用例“星形中心点中心度 = 1、叶子点 = 1/(N−1)”。
    - §5 合并一行与 LP-9 按决定 2～4 修改；§1 的函数输入须包含谱系，或写明由调用方投影后再传入。
    - 须补的验收：`m` 已掌握、`p` 未知 → `p` 有效为已掌握，`m` 迁到 `p` 的后继按新前置判定；`p` 为 learning、`m` 为 mastered → mastered；链式合并；回滚使 `m` 重现 → 各用自己的记录；进度行在各步骤前后字节不变。
  - **A08 修复须提出、并另行签收的细则**：
    1. **学生如何取消继承来的状态**。按决定 2 取最高值，学生在 `p` 上标“未知”后仍会被 `m` 的 mastered 顶回去。须规定合并生效后学生对 `p` 的显式写入优先，并给出判定依据，例如与合并首次发布的时间比较。
    2. **谱系存在哪里**。可以作为快照字段写入每个版本（如节点的 `merged_from`），这属于 ADR-012 的修订，但与版本绑定、回滚天然一致；也可以作为课程级追加表，配合“来源不在版本中才继承”的规则。审查建议前者。
  - **F10（合并服务）**：合并时持久化 `merged_ids → primary_id` 谱系；`MergeRequest` 形状不变。
  - **I01/I03**：进度投影按决定 2～4 实现；I03 的纯函数接收已投影的掌握集合。
  - **不受影响**：四项权重、可学集合定义、A08 §7 的其余待签收项（量纲、缺失中性值、权重配置来源、推荐上限），仍按原状态待签收。
- **推翻条件**：
  1. 教师反映合并的往往不是同一概念，而是“相近但不同”的知识点，继承导致学生越过实际没学的内容时，重开决定 2，考虑由教师在合并时选择是否继承。
  2. 实测中度中心度对排序几乎没有区分度（稀疏图中大多接近 0）时，重开决定 1，改用方案 2。

### ADR-014 修订 1：A08 §7 参数、进度接口字段与两项细则（A08 签收）

- **日期**：2026-09-23
- **背景**：A08（`specs/learning-path.md`，PR #19）经三轮审查合入 main 后，§7 仍有四项提案待签收：属性缺失时的中性值、权重来源、推荐上限，以及进度接口的新增字段。本条“后果”交给 A08 的两项细则也待签收：学生如何取消继承来的状态，以及谱系存放位置。审查报告 `docs/reviews/claude-codex-a08-r2-2026-09-23.md` 的 R15 指出，细则 1 的原提案在“回滚后再合并”时有两种读法，必须先写死。
- **评估方案**：

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 权重来源 | 1. 环境变量，缺省为 S2 值 | **采纳** | 符合 AGENTS.md“配置只能从环境变量读取”；LP-5 的校验仍有意义；实测时便于调参 |
  | 权重来源 | 2. 代码常量 | 否决 | 最简单，但改权重要改代码 |
  | 权重来源 | 3. 课程级配置 | 否决 | 需要新增持久化与 DTO，还要决定生效时机和是否随快照冻结，不适合 MVP |
  | 显式写入覆盖继承 | 1. 以来源本次连续归属的起点为界 | **采纳** | 回滚让来源重新出现就中断，再次合并时重新起算，学生在回滚期间对来源的标记不会被旧写入吞掉 |
  | 显式写入覆盖继承 | 2. 以来源第一次并入为界 | 否决 | 回滚后再合并时，主节点的旧写入会压过来源更晚的标记 |
  | 显式写入覆盖继承 | 3. 不设覆盖，维持取最高 | 否决 | 学生无法取消继承来的状态 |
  | 谱系存放位置 | 1. 发布快照节点字段 `merged_from` | **采纳** | 与版本绑定、回滚天然一致 |
  | 谱系存放位置 | 2. 课程级追加表 | 否决 | 需要有效版本区间和回滚重放语义，且可能出现环 |

- **决定**（接续决定 1～4）：
  5. **缺失属性的中性值**：知识点缺 `importance` 或 `difficulty` 时取 0.5；字段存在但非有限或不在 `[0,1]` 内，按已提交版完整性错误处理。
  6. **权重来源**：四个环境变量 `RECOMMEND_WEIGHT_UNLOCK`、`RECOMMEND_WEIGHT_IMPORTANCE`、`RECOMMEND_WEIGHT_CHAPTER`、`RECOMMEND_WEIGHT_EASE`。四项都不设时使用 S2 缺省值 0.35/0.25/0.20/0.20；四项都设时使用所设值；只设一部分则拒绝启动。所设值须满足 A08 §1 的校验（有限、非负、和在 `1 ± 1e-9` 内、至少一项为正），不满足则拒绝启动。进程启动时读取一次，全站统一；不做课程级配置，学生请求不能传权重。
  7. **推荐上限**：`limit` 为正整数，默认 10，最大 50；超出范围的请求被拒绝。
  8. **进度接口**：`GET /progress` 与成功的 `PUT /progress` 都返回绑定版本 V 中的**每个**节点。每项包含：
     - `status`：有效状态，与推荐使用同一投影；
     - `own_status`：学生自己的原始状态，没有记录时为 `null`；
     - `inherited_from[]`：参与取最高的来源，即未被决定 9 覆盖的来源，每项为 `{kp_id, status}`，按 `kp_id` 的 UTF-8 字节序排列；
     - `updated_at`：只表示自身记录的更新时间，没有自身记录时为 `null`。

     字段由 B12 写入 YAML 真源。
  9. **显式写入覆盖继承**（细则 1，修订决定 2 的“取最高”）：设来源 `m` 在绑定版本 V（版本号 `n`）中按 A08 §5 的链规则归属到可见节点 `p`。
     - **起算版本 `k`**：从 `n` 起逐个往前检查已提交版本，`k` 是 `m` 连续归属到 `p` 的最早一个。回滚使 `m` 重新出现即中断连续，再次合并时从新版本起算。
     - **界 `T`**：版本 `k` 的提交序号。
     - **覆盖**：`p` 自身记录的写入序号大于 `T` 时，`m` 被覆盖，既不参与 `p` 的取最高，也不列入 `inherited_from[]`；否则 `m` 照常参与。

     `p` 的有效状态取 `p` 自身记录与所有未被覆盖来源中的最高者。写入序号与提交序号取自 SQLite 中同一个单调序列，分别在进度写入事务和版本提交事务内取号；不使用客户端时间、`updated_at` 或 `committed_at`。起算版本在读取时计算，可按 `version_id` 缓存，不写入快照。由此可推出：合并生效后，学生对 `p` 的任何显式写入都会覆盖当前归属到 `p` 的全部来源。

     **补注（Codex A08S-R01，推导细则，ArvinHan 2026-09-24 签收）**：同值写入不能只凭原始 `status` 相同就跳过。在提交时的最终绑定版本上，若 `p` 仍有未被覆盖的来源，同值写入也是一次显式写入，取新写入序号并覆盖它们；没有时才为无操作（不取序号、不改 `updated_at`）。因此同一绑定版本下的重放从第二次起为无操作。见 A08 §5「同值写入」与 LP-16、LP-18。
  10. **谱系存放位置**（细则 2）：谱系作为发布快照中节点的 `merged_from` 字段保存，按绑定的 `version_id` 读取；回滚复制源快照时，谱系随之回退。字段形状（包括链式来源与直接父子关系的表示）以及它如何进入快照摘要，由 ADR-012 的下一次修订规定。

## ADR-015：问答在检索后开流、流内逐引用校验、模型以哨兵声明证据不足、非 answered 结局一律撤回临时正文

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-23。本条由原子任务 **A09** 提交。决定方向由 ArvinHan 在会话中逐项选定（流式方案、证据不足的表达、截断按默认、问答记录命名），四节设计逐节确认，书面条文随后签收；签收范围含设计讨论后补的两处细化：最终结果也带 `request_id`（JSON 模式无 `meta`），同一对话同时最多一个在途请求。
> 规范文本只有一份，在 `specs/grounded-qa.md`「问答终态与引用撤回协议」Q1～Q12（含 QA-1～35 验收）；本条只记录决定与理由，不复制矩阵。
> **编号说明**：ADR-014 由 A08 使用；A10 的 ADR-016（PR #18）已写明 015 留给 A09。本条取 015。

- **日期**：2026-09-23
- **背景**：
  1. **R03/R04 只修了结构**。`740adb` `978671e` 已把 `ChatResponse` 拆成 `answered` / `not_covered` 判别联合、给每种 `ChatEvent` 独立 schema，并规定 `done.final` 为唯一权威正文。仍未定义的是：已出字后 `error` 时临时正文怎么处理；流异常结束与用户取消；引用编号格式（没有它，「删除无效引用」无法精确描述）；检索失败而 `meta` 必须为首条时的事件顺序；`out_of_course_scope` 由谁判定；多轮 `history` 中的助手回合能否携带引用。

  | 问题 | 方案 | 结论 | 理由 |
  | --- | --- | --- | --- |
  | 流式正文与最终答案 | 流内逐引用校验，无效标记当场剔除 | **采纳** | `answered` 时最终正文恒等于 delta 拼接，屏幕上的字不会变；撤回只发生在非 `answered` 结局；只需暂扣少数字符，首字时延不变 |
  | 流式正文与最终答案 | 原样流出、终态整体替换（`740adb` 草稿） | 否决 | 服务端最简单，但 `answered` 时学生也会看到编号在最后一刻消失，前端必须做整段替换 |
  | 流式正文与最终答案 | 不流正文，只发终态 | 否决 | 永远无需撤回，但放弃「首字 ≤ 3 秒」目标 |
  | 模型判定资料不足 | 输出开头的固定哨兵 + `out_of_course_scope` 改名 `insufficient_evidence` | **采纳** | 命中即停止生成、不下发任何正文，省 token；四个原因中两个不调用生成、两个调用了生成，日志与文案都能区分 |

- **决定**：
  1. **分段与文法**：鉴权、版本绑定、问题改写、检索、阈值判定都在开流前完成，其中的失败是普通 HTTP 错误（两种模式一致）；改写失败不报错、改用原问题。开流后事件序列为 `meta delta* (done | error)`，`meta` 恰好一条且为首条，`done` / `error` 互斥、恰好一条。`meta` 与 `final` 增加 `graph_version`、`request_id`。客户端断开时服务端停止生成、不再发事件、不自动重新生成。
  2. **流内逐引用校验**：只给同课程、属绑定版本修订列表、可定位的文本块编号；规范标记为 `[n]`；归一化是闭集（列表展开、全角括号）；无法归一化的类标记与编号不在集合内的标记当场剔除；代码片段内不识别。不变式：`answered` 时 `final.answer` 等于已下发 delta 的逐字拼接，且正文标记集合等于 `citations` 编号集合、非空。
  3. **证据不足**：模型以 `<<INSUFFICIENT_EVIDENCE>>` 开头声明资料不足，服务端暂扣开头至多 25 个字符判定，命中即关闭供应商流、不下发正文。`NotCoveredReason` 的 `out_of_course_scope` 改为 `insufficient_evidence`。
  4. **终态与撤回**：终态矩阵 O1～O15 以规格为准。唯一保留正文的结局是 `done` 且 `answered`，其余一律整段清除临时正文、不自动重试。已出字后中断与链路超时都不把已生成部分校验成答案。输出截断按正常结束判定。问答的 `LLM_UNAVAILABLE` 以 `details.reason ∈ {upstream, stream_interrupted, timeout, auth}` 区分，不新增超时错误码。
  5. **未覆盖文案**：`not_covered` 的 `answer` 由服务端按 `reason` 套固定模板，绝不含模型输出。
  6. **多轮历史**：服务端不保存会话；历史只作问题改写的输入，改写前剔除类标记与哨兵；生成提示不含历史。客户端只放 `answered` / `not_covered` 回合。`kp_id` 只引导检索，不在绑定版本中则忽略。
  7. **跨版本**：回答钉在绑定版本；重新发布或回滚不追溯撤回既有回答的引用；界面对旧版本回答标注版本号。
  8. **命名**：问答记录实体 `ChatLog`、表 `chat_logs`（关闭 A10 N5）。

## ADR-018：分块版本并入解析器版本，块 ID 随分块规则或参数变化而更新

> **签收状态：已签收（ACCEPTED）**，ArvinHan，2026-09-25（在会话中选定「并入 `parser_version`」）。本条由协调方在 D09（#226）合并前记录。
>
> **修订 1（本条末尾，2026-09-25 签收）**：解析器段内多个处理步骤用 `,` 连接、按处理顺序排列；`+` 只作解析器段与分块段的分隔符。PDF 流水线版本定为 `pdf/1,cleanup/1,headings/1`。

- **日期**：2026-09-25
- **背景**：ADR-012 修订 1 决定 9 规定资料修订为 `(material_id, 内容哈希, 解析器版本)`，块 ID = `revision_id` + 块序号，块一经写入不可变。D09（#226）实现时发现：块序号和块文本由 D08 分块器决定，而分块规则与参数（`target_chars`、`overlap_chars`）不在修订键中。只改分块、不改解析器版本时，同一块 ID 会对应不同文本，D10 的不可变检查会拒绝写入，处理失败。可选方案：分块版本并入 `parser_version`；或在修订键中另加字段。
- **决定**：
  1. **修订键里的 `parser_version` 是复合版本**：`<解析器版本>+<分块版本>`，例如 `pdf/1+chunk/1@1500-200`。修订键的字段、`revision_id` 公式与块 ID 公式都不变，不另加字段。
  2. **分块版本 = 分块规则版本 + 实际参数**：形如 `chunk/<规则版本>@<target_chars>-<overlap_chars>`。规则版本由 D08 `chunking.py` 的 `CHUNKER_VERSION` 常量给出，分块输出规则变化时递增；参数取本次实际使用的值，因此改默认值或传入非默认参数都会得到新修订。
  3. **拼接只在 D09 一处**：D09 提供组合函数，D11 编排时用解析器给出的 `parser_version` 和分块版本组合后写入修订键；各解析器模块的 `PARSER_VERSION` 仍只表示解析器自身。`revision_id` 拒绝不含分块段的 `parser_version`，防止编排时遗漏。
- **后果**：
  - D09（#226）追加：组合与校验函数及测试；D08 的 `chunking.py` 增加 `CHUNKER_VERSION` 与分块版本函数，属范围扩展，由本 ADR 授权。
  - `docs/architecture.md`「资料修订」一行与 `specs/teacher-review-publish.md` 资料修订一条补注复合版本；D10/D11 按本 ADR 写入。
  - 分块规则或参数一变，已有资料再处理即产生新修订与新块 ID，抽取缓存随块 ID 失效；已发布版本按修订固定，不受影响（与 PUB-29 同理）。
- **推翻条件**：分块参数需要按课程或按资料频繁调整，导致修订数量失控时，重开决定 2，改为参数只进缓存键。

### ADR-018 修订 1：解析器段内的步骤用 `,` 连接

- **日期**：2026-09-25
- **背景**：D06（#208）把带标题判定的 PDF 版本写成 `pdf/1+headings/1`，内部用了 `+`；而决定 1 以 `+` 分隔解析器段与分块段，D09 因此拒绝该版本。D11（#239）在 worker 里临时改用 `pdf/1,cleanup/1,headings/1`。块 ID 由版本字符串派生，必须在真实 PDF 块入库前定下格式，否则之后再改，同一份 PDF 会得到新修订与新块 ID。
- **决定**：
  1. **解析器段的格式**：一个或多个 `<名称>/<版本>` 用 `,` 连接，不含空白；名称为小写字母开头的 `[a-z0-9_-]`，版本为无前导零的正整数（ASCII）。`+` 只作解析器段与分块段的分隔符，任何段内都不得出现。D09 `revision_parser_version` 与修订键校验按此格式校验。
  2. **顺序即处理顺序**：多步骤解析按执行顺序列出各步骤版本；只有一步的格式（`txt/1`、`docx/1`、`markdown/1`）不变。
  3. **PDF 版本常量由 D06 给出**：`pdf_headings.PARSER_VERSION = "pdf/1,headings/1"`（不清洗的 `parse_pdf_with_headings`）；`pdf_headings.CLEANED_PARSER_VERSION = "pdf/1,cleanup/1,headings/1"`（D05 提取 → D07 清洗 → D06 标题判定）。D11 编排 PDF 时引用 `CLEANED_PARSER_VERSION`，不在 worker 里另拼字符串。
  4. **清洗参数**：D11 只用 D07 的默认阈值；清洗规则或默认阈值变化时递增 `CLEANUP_VERSION`。若将来需要非默认阈值，先修订本条。

## ADR-024：F04 草稿节点与来源关联的图模型；加锁节点完全不动

- **日期**：2026-09-26
- **背景**：§8.4 规定了贡献记录（`contrib_tasks`、`contrib_manual`、来源关联带 `task_id`），但没有定来源关联在 Neo4j 中的类型与属性、共享 `Chunk` 节点带哪些字段，也没有定加锁节点遇到新资料里的同名知识点时能否补来源（`specs/teacher-review-publish.md`「待细化」列有加锁粒度）。

## ADR-025：F06 关系写入的课程守卫节点、关系属性与既有关系的处理

- **日期**：2026-09-26
- **背景**：F06 验收要求「两个连接并发 A→B / B→A 至少一方冲突；校验与提交同写入序列」。Neo4j 默认读已提交，两个事务各自读图、各自通过环检测后都能提交；只锁端点也不够（A→B、C→D 先提交后，B→C 与 D→A 的端点互不相交，仍会同时通过）。V4 的 SQLite 课程写锁（`course_locks`）尚未建表，且租约过期后可能与晚到的写入重叠。§8.4 只说关系来源按「(贡献方, 文本块 ID)」成对保存、编码由 F03/F13 定。
- **决定**：
  1. F03 迁移新增 `DraftWriteGuard(course_id, version_id)` 唯一约束。每个关系写事务第一条语句 `MERGE` 本课程草稿的守卫节点并递增 `seq`，持有它的写锁直到提交；读图、环检测（F05）与 `MERGE` 都在其后、同一事务内。同一课程草稿的关系写入因此串行，与 SQLite 课程写锁互为冗余。
  2. F02 `Neo4jRepository` 新增 `write_transaction(scope, work)`：一个显式写事务内多条语句，每条都经同样的作用域参数校验；驱动的临时故障可能让 `work` 重跑，`work` 须只依赖事务内读到的数据；`work` 自己抛出的异常回滚后原样抛出，驱动异常仍脱敏。
  3. 关系属性：`course_id`、`version_id`、`rel_id`、`confidence`、`status`、`source`、`contrib_tasks`、`contrib_manual`、`revision`、`source_pairs`；`source_pairs` 每项是 JSON 字符串 `[贡献方, chunk_id]`，人工贡献方为 `null`。`RelationIdentity` 记当前 `type`、`from_id`、`to_id`。
  4. 关系 ID 由「课程 + 类型 + 起点 + 终点」派生；`RELATED_TO` 还可使用同端点 `PREREQUISITE` 的 ID（ADR-009 降级保留原 ID）。
  5. 已有同 ID 关系时：教师写入遇到可见关系、或类型/端点不同 → `DUPLICATE_RELATION`；遇到不可见关系（未提交或失败任务留下）由教师接管字段。任务写入从不改已有关系的字段：端点不同（教师改过端点）跳过并报告；类型不同（降级或教师改类型）沿用现有类型，只并入贡献与来源。
  6. 一次调用全有或全无：端点不可见 → `DANGLING_ENDPOINT`；成环 → `CYCLE_DETECTED` 带闭合环路；`PREREQUISITE` 自环不连库即返回 `[A, A]`，其他类型自环为非法输入。
- **后果**：教师新建/修改关系（F08）与 F13 `persisting` 都能在同一事务里复用这些语句；F13 的自动降级在锁内、同一次读取上计算。守卫节点让同一课程的关系写入不能并行，吞吐按课程串行（与课程写锁一致）。Neo4j 等锁默认无上限，靠 V4 的 API 侧有界等待兜底。
- **回滚**：撤销 `graph_relations.py`、`services/graph/relations.py`、`write_transaction` 与测试；守卫约束可 `DROP CONSTRAINT draft_write_guard_scope`，守卫节点可 `MATCH (g:DraftWriteGuard) DELETE g`，不影响知识点与关系。
- **签收**：待 ArvinHan 审阅（守卫节点与属性编码由 Claude 选定并在交接中报告）。

  2. **状态一律 `draft`**（ArvinHan 在会话卡片上选定），置信度原值保存（缺失记 0）；D-08 签收后按阈值重算。ADR-009 降级的关系仍为 `low_confidence`。
  3. 迁移 009：`course_locks(course_id 主键, holder, token, expires_at)` 与任务租约同构；`processing_tasks.t6_seq` 在 T6 事务里取本课程最大值 + 1，`(course_id, t6_seq)` 部分唯一索引。
  4. `persisting` 流程：取课程写锁（持锁期间每 `L/3` 续约；等锁上限为一个锁租约 `L`，仍拿不到则按存储临时故障释放退避）→ 复核租约 → 读 V → **一个 Neo4j 写事务**：锁守卫节点（ADR-025）、撤销本任务全部贡献并删除因此无贡献的元素、F04 写节点、按 ADR-009 逐环降级（`plan_downgrades`，选环上置信度最低、并列取 `rel_id` 最小的可降级边）、F06 写关系 → T6（分配序号、清空租约，并递增 `courses.draft_revision`：任务内容此刻变为可见，已发布课程据此显示为 `revising`）→ 释放锁。
  5. 失败：Neo4j/SQLite 故障与等锁超时 → `STORAGE_UNAVAILABLE` 释放退避，耗尽则 T9；环上无可降级边 → T9 `CYCLE_DETECTED`；其余 → T9 `INTERNAL_ERROR`。`persisting` 的任何 T9（含 C09 回收与释放时的耗尽）都置 `cleanup_pending`，随后在课程写锁下撤销本任务贡献，成功才清除；回收步骤对遗留标记重试。
  6. 找环用 F05 `find_cycle`（按节点 ID 升序 DFS），而非规格原文「按边 ID 升序遍历邻接」；两者都只依赖边集合，结果可复现（DAG-3），降级选择规则不变。
- **后果**：上传的资料能一路走到 `awaiting_review`，但同名知识点在不同资料间不合并，直到融合接入。直通模式下本任务的节点 ID 由任务派生，跨任务成环只可能来自草稿里已有的环（DAG-10）；降级他人未确认边的路径已实现，由纯函数测试和 `downgrade_relation` 覆盖。等锁超时会消耗一次尝试。
- **回滚**：停 API 与 worker，按迁移 009 文件头的 `ROLLBACK` 行删表与列（`test_f13.py` 已验证），撤销 `persist_graph.py`、`course_locks.py`、`downgrade.py` 与相关改动；处于 `merging`/`persisting` 的任务会停在原阶段，直到新的 worker 接手。
- **签收**：ArvinHan 2026-09-26 在会话卡片上选定第 1、2 条；其余由 Claude 选定并在交接中报告。

## ADR-030：F07 图谱读取入口、读取时计算层级与来源定位

- **日期**：2026-09-26
- **背景**：契约 `getGraph` 只写了「教师读草稿、学生读已发布」与 `version` 参数，没有定：教师带 `version` 读什么；课程未发布、版本不存在、图为空三者如何区分；`KnowledgePoint.level` 由谁计算；`SourceRef` 的页码/章节从哪来（Neo4j 的 `EVIDENCED_BY` 只有块内证据区间，§8.4 与 ADR-024）。历史版本表（G02）与发布快照（G04）都还没有。
- **决定**：
  1. **读入口**：教师不带 `version` 读草稿，V 在请求开始时从 SQLite 读一次（§8.4），节点、章节、关系、来源关联都按 V 过滤，关系另要求两端可见。学生（C03 已先拒绝未发布课程），或教师带 `version`，读当前发布版本 `courses.published_version_id` 的副本，不按 V 过滤。
  2. **空图与未发布**：空草稿、空的已发布版本返回 200 与空 `nodes`/`edges`；没有发布版本时 404 `GRAPH_NOT_PUBLISHED`；`version` 不等于当前发布版本号时 404 `NOT_FOUND`（历史版本读取待 G02 建版本表后补）。
  3. **`level` 读取时计算**：取返回课程图（过滤前）中非 `rejected` 的 `PREREQUISITE` 边的最长前置路径；草稿若违反 DAG，环上节点为 0。存储里不写 `level`。
  4. **来源定位**：`SourceRef` 的 `page`/`section_path` 取自 SQLite 按本课程读出的块（D10）。知识点来源按证据区间在块文本中的位置找对应解析块（与 E05 抽取时相同的拼接规则），另带该区间的原文 `text`；关系来源取 `source_pairs` 中可见贡献方的块的第一个出处。无法定位的来源（块不在本课程、无定位字段）丢弃并记日志；知识点一条可定位来源都没有时 500 `INTERNAL_ERROR`（违反 `source_refs` 至少一条）。
  5. Neo4j 不可达 → 503 `STORAGE_UNAVAILABLE`；可选字段省略而不是写 `null`，`graph_version` 总是返回（草稿为 `null`）。
- **后果**：前端和学习路径可以直接用 `getGraph` 的 `level`；每次读取都会整图计算层级，课程规模（数百节点）下可以接受。人工添加且没有来源的知识点在详情接口上会是 500，F08 需保证教师新建知识点时至少带一条来源，否则要回来改契约。
- **回滚**：撤销 `api/graph.py`、`services/graph/read.py`、`repositories/graph_read.py`、`main.py` 一行注册与测试；无数据变更。
- **签收**：待 ArvinHan 审阅（入口语义与 500 处理由 Claude 选定并在交接中报告）。

## ADR-031：G01 快照组装的边界情形

- **日期**：2026-09-26
- **背景**：`specs/teacher-review-publish.md` V3 定了发布集合、校验原因、快照格式与规范化，但留下几处实现细节：快照章节的 `parent_id` 在契约 `Chapter` 中不存在；降级关系的 `downgraded_from_type`/`downgrade_cycle` 是否进快照；`low_confidence` 或 `rejected` 关系端点不存在时是否阻断；`rejected` 是否计入 `excluded`；输入结构错误如何与发布阻断区分。
- **决定**：
  1. 快照章节按 V3 示例带 `parent_id`（无则 `null`）；发布集合的章节为被引用章节及其在草稿中的祖先，保证 `parent_id` 可解析。
  2. 降级字段不进快照：降级关系必为 `low_confidence`（契约 `RelationDowngraded`），本就被排除；教师通过后成为普通关系。
  3. 端点不存在按「草稿不变量被破坏」处理：除 `rejected` 外，`draft`/`approved`/`low_confidence` 关系都检查并报 `dangling_endpoint`；`rejected` 关系不在任何集合里，不检查。
  4. `excluded` 只计 `low_confidence` 知识点与关系，`rejected` 不计；端点被 `low_confidence` 或 `rejected` 排除的关系计入 `cascaded_edges`。
  5. 所有阻断原因一次报全，顺序固定为 `cycle`、`dangling_endpoint`（按关系 ID）、`invalid_source_ref`（先知识点后关系，各按 ID）、`empty_graph`、`invalid_lineage`（按知识点 ID）。
  6. 输入结构错误（重复 ID、非法类型/状态、非有限数值、区间外的难度与重要度等）抛 `SnapshotFormatError`，属实现缺陷，由 G04 按 5xx 处理，不作为 `PUBLISH_BLOCKED` 返回；`load_snapshot` 只接受规范形态的字节，读出即可复算摘要。
- **后果**：G04 在 P4～P7 持锁读出可见草稿后直接调用 `build_snapshot`；G03 物化与 P9 核对用 `load_snapshot` 读回。今后若给学生可见字段加项，须同时改快照与 `snapshot_format`。
- **回滚**：撤销 `services/versions/` 与 `tests/backend/test_g01.py`；无数据变更。
- **签收**：待 ArvinHan 审阅（以上细节由 Claude 选定并在交接中报告）。

## ADR-032：G02 版本表的实现约定

- **日期**：2026-09-26
- **背景**：V2 给出了 `graph_versions` 的字段语义与部分唯一索引，但没有定：G02 验收里的「幂等键」指什么；P11 的提交、指针 CAS 与 T7 怎样放进同一事务；已提交版本如何在库层面防改；租约与审计时间的单位。
- **决定**：
  1. **幂等键就是尝试的 `version_id`**（ULID，开始时生成、永不复用）。同一尝试重复提交时，第二次因行已不是 `materialized` 被拒，版本数与 `commit_sequence` 都不变；重复使用 `version_id` 插入违反主键。「同一内容不产生新版本」由 G04 的摘要比较（P7 幂等路径）负责，G02 提供 `discard_attempt`。
  2. `commit_attempt` 与 `discard_attempt` 接收调用方的写事务，只做 P11/R7 第 1、2 条（分配版本号与提交序号、指针 CAS）或幂等路径的删除与 `published_from_revision`；条件不成立抛 `CommitRejected`，调用方回滚整个事务（含 T7）。版本号取本课程已提交最大 + 1，`(course_id, version)` 与 `commit_seq` 各有部分唯一索引。
  3. 表约束保证状态与字段一致：只有 `committed` 行有版本号、提交序号与提交时间；只有 `failed` 行有失败原因、可置 `cleanup_pending`；`materialized` 与 `committed` 必有快照与摘要；回滚行必有 `source_version`。
  4. 触发器禁止删除 `committed` 行、禁止修改其内容，只放行 `embedding_space`（V12 重新向量化）。
  5. `expires_at` 为 SQLite `unixepoch()` 秒（与 `course_locks` 一致）；`created_at`/`committed_at` 为 ISO-8601 UTC 文本。`course_id` 外键指向 `courses`；`created_by` 可空（命令行操作）。
  6. `commit_sequence` 单行表由本迁移创建并插入 `(1, 0)`，版本提交与进度写入共用（ADR-012 修订 3）。
- **后果**：G04/G06 可以在一个 `immediate()` 事务里组合 `commit_attempt` 与 T7；G05 的清扫用 `fail_attempt`/`set_cleanup_pending`。F13 的迁移 009 回滚测试改为先回滚更新的迁移（按编号倒序），因为迁移器拒绝在已有更新版本时重放旧迁移。
- **回滚**：按迁移 010 文件头的 `ROLLBACK` 行回滚（`test_g02.py` 已验证），或恢复 `backups/*-before-010.sqlite`；撤销 `repositories/versions.py`。
- **签收**：待 ArvinHan 审阅（以上约定由 Claude 选定并在交接中报告）。

## ADR-033：G03 版本副本的形态与读取

- **日期**：2026-09-26
- **背景**：V2/V5 规定版本副本「只含快照字段 + 知识点向量 + 作用域字段」，P8 在一个 Neo4j 写事务内物化、P9 读回复算摘要。未定的是：知识点向量用什么文本；来源边的类型（V2 写 `EVIDENCE`，而草稿按 ADR-024 用 `EVIDENCED_BY`）；关系来源怎么存；契约 `KnowledgePoint`/`Relation` 要求 `status`、`confidence`、`source`、`locked`、`revision`，而副本按规定不带这些字段，F07 读已发布版本时怎么办；重试怎样保证不重复。
- **决定**：
  1. 知识点向量文本为「名称 + 换行 + 定义」，经 E07 适配器按当前空间计算；写入前逐个核对空间标识与维度（F03 `_validate_vector`），缺向量或不符即在连库前失败。
  2. 副本的来源边沿用 `EVIDENCED_BY`（只带 `chunk_id`，无 `task_id`、无证据区间），与草稿同名，F07 读取不分版本；V2 的 `EVIDENCE` 视为 ADR-024 之前的叫法。
  3. 副本关系存 `source_refs`（块 ID 列表），不存 `source_pairs` 与贡献记录。
  4. P8 在同一写事务里先删除本 `(course_id, version_id)` 的全部副本再重建，重试同一尝试得到同一张图；来源块或端点缺失时整体回滚。P9 从 Neo4j 读回章节、知识点、来源与关系，`revisions` 取自快照本身，复算摘要必须相等。
  5. F07 读已发布版本时，副本缺少的契约必填字段按「已发布」补齐：`status = approved`、`confidence = 1.0`、`source = manual`、`locked = false`、`revision = 1`。F07 的节点查询改为显式投影，不把向量属性带回应用层。
- **后果**：学生端看到的已发布知识点状态恒为 `approved`，来源类别恒为 `manual`，与草稿里的真实值无关；如果前端需要展示真实来源类别，须改规格让它进快照（并使 `snapshot_format` 加 1）。知识点详情里已发布版本的来源不带原文片段（副本没有证据区间），只有页码或章节路径。
- **回滚**：撤销 `services/versions/materialize.py` 与测试，恢复 F07 的两处改动；已物化的版本副本可按 `(course_id, version_id)` 删除。
- **签收**：待 ArvinHan 审阅（第 1、5 条的取值由 Claude 选定，是学生能看到的输出，请重点确认）。

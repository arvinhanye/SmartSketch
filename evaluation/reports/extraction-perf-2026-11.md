# EXTRACT-PERF-01：图谱生成性能测量

日期：2026-11-05。状态：按用户确认范围交付生成调度与默认8；图库根因与修复转后续专项，发布按用户决定延期。代码起点 `ad63341`，分支 `codex/extraction-perf`。
OPT-05 在源工作区尚未提交，按交接 §1 使用独立 worktree，发布向量化文件暂不修改。
本轮无付费模型调用，假模型结果不能证明真实准确率或真实模型的 ≤60 秒验收。

## 测量口径

- 材料：`datasets/demo/ch3-stack-queue.md`，11,779 字节。
- 当前解析实际得到 16 个语义块、16 个小节，5,819 字符，平均 363.69 字符。
- 使用 `scripts/fake_provider.py`，每次实际生成请求固定等待 8 秒；并发 4 为旧默认基线，并发 8 先实验，再经用户确认改为默认。
- 上传发起到任务 `awaiting_review` 为生成耗时；发布另外计时，不混入生成。
- 实体和关系允许重叠时分别列跨度、交叠和并集，不能把两段跨度直接相加。
- `persist steps` 的 `t6` 位于 `neo4j` 计时内部，不能重复相加。冷启动、同机并行负载必须注明。

历史真实基线（L02，单次测量，旧代码/旧环境，仅供参照）：

| 阶段 | 秒 |
| --- | ---: |
| 排队、解析、分块 | 约 1.4 |
| 实体＋关系＋修复跨度 | 约 94.4 |
| 最后模型完成至待审核 | 约 45.7 |
| 上传至待审核 | 141.72 |
| 发布，含在线向量化 | 21.17 |

L02 的 8.5 秒实体、10.5 秒关系是**平均**调用耗时，并非交接转述的 p50。
固定 8 秒下若实际为 16 次实体＋15 次关系，旧屏障耗时下限为
`ceil(16/4)×8 + ceil(15/4)×8 = 64` 秒；共享池下界也是 `ceil(31/4)×8 = 64` 秒。
不能预先声称去屏障会明显加速这个均匀延迟样例；慢尾块的结构性收益另用确定性交错场景验证。

## 已核实的优化边界

1. 用户已决定采用保守去屏障：实体块优先，只有剩余块即使全部失败也不会超阈值时，小节才能填空；小节全部成员结束后，仅以成功成员构造原有模型输入。既有超阈值无关系检查点断言保留。
2. `runner.run_loop → run_pipeline_once` 在一次领取、同一租约与心跳内连续推进所有阶段；`IDLE_SECONDS=2` 只用于无任务时等待。阶段交接没有固定 2 秒轮询，不修改 runner。
3. 实体、关系、repair 已全部使用 JSON 输出模式。没有“开启 JSON 模式”的新增收益。
4. repair 原因包括坏 JSON、顶层结构错误、截断。L02 的三次 repair 首因未留存，不能补造分布；C03-1 的两次关系 repair 有推理耗尽 4096 输出上限的历史证据。条目级校验丢弃不会触发 repair。
5. 提前关系会改变共享预算/熔断器的消费顺序；在预算紧张或供应商故障时，不能把正常输入/输出等价扩大为所有故障交错完全一致。计费规则、阈值和停止派发约束须回归验证。
